# TUI transcript 折叠改造方案

状态：**批次一至十八已实施，批次六未实施**（批次九推翻了批次七「思考结束过程」的决定，见下文）。v2 依据 DeepSeek Harness 官方 Web 客户端（`refs/deepseek-harness`，tag `dsh-v0.2.0-rc.1`）的实际实现重写了 v1 的两个核心决策，并引入官方采用的两级折叠模型与策略表。v3 记录批次一的实际落地结果与三处 omdsh 自主决策。

## omdsh 的自主立场

三个参考项目（DSH Web、oh-my-pi、pi）都是**证据来源，不是模板**。批次一落地时有三处明确偏离了参考实现，理由是 omdsh 已有更好的答案：

**P1 · 状态归页脚，transcript 只记事实。** 官方 Web 在组头上重复活动状态与 `liveProcessDetail` 标题；omdsh 已有常驻的两行状态栏承担"现在在做什么、花了多久"。折叠行因此**不画 spinner 相位、不画耗时、不写 running 字样**——重复一遍只会让两个地方打架。状态只有一个来源。

**P2 · 复用既有展示层，不新造摘要层。** 官方需要 `deriveSummary`，因为它的 `ToolCallView` 常常给不出标题，必须从原始参数里反推。omdsh 已经有完整的 `renderTool`，为每个工具族算好了语义 title 与尾部事实。批次一直接复用它，只补了一个 `toolArgSubject` 处理"无 card 时原始参数对象被 pretty-print 成 `{`"这个真实缺口——这比移植整个 `deriveSummary` 少一层概念。

**P3 · 边框只表示"你打开过它"。** `AGENTS.md` 既有规则要求"边框只在表达真实组件边界或交互状态时使用"。批次一最初让成功调用不带框、失败调用保留框，于是边框表示"这里有值得读的内容"；批次二按 DSH Web 的做法改成失败也折成一行（错误文本即那一行的事实，详见 E2），边框因此只剩下一个含义：**读者打开过它**。成功与失败一视同仁，都默认一行，唯一的差别是那行末尾写什么。

**P5 · 不把 reasoning 拆成独立的 block。** 官方把 assistant 消息的内容建模成 `AssistantBlock` 五路联合（`text | reasoning | image | tool-call | other`），于是思考天然是一个可寻址、可折叠的单位。我们没有照搬这个形状：`reasoning` 仍是 assistant block 上的一个扁平字符串，折叠态用一个 `turn:step` 键挂在 provider 侧。理由是收益不成比例——拆成独立 block 会牵动 replay、resume 和旧日志兼容，而批次三要解决的是"别把思考铺满屏幕"，段落边界预览一行就够。批次四做 turn 分组时再一起决定形状，届时如果分组需要一个"一个 assistant 可以贡献 reasoning 到组、贡献回答到组外"的能力，才真的需要 `groupPart` 那种结构。

**P6 · 组是渲染投影，不是新的 block。** 官方把分组做成 transcript 里的一等对象（`GroupSnapshot` + 独立位置索引 + 渲染入口列表），因为它的折叠控件活在一个 React 树里。我们没有照搬：`processGroups(blocks)` 是 `state.blocks` 上的纯投影，渲染循环据此决定哪些 block 出行、组头占掉第一个 block 的行。代价是折叠组内部的 block 不可寻址，收益是 block 列表、搜索下标、focus 下标和 `blockStarts` 全部保持原语义，不用动 `event-views.ts` 的事件折叠。

代价怎么闭合：**凡是读者能寻址的 block（搜索命中、被 focus 的那个）强制展开它所在的组**。这两条规则是承重的 —— 去掉任一条，那条测试立刻失败，因为命中下标会指向一个不存在的行。组内的 block 仍保留一个合法偏移（永远小于帧高），focus 的 clamp 不会把读者送到无意义的位置。

另外两条偏离参考实现的地方：

- **一个组里有失败就不折叠。** 官方是按 turn 的结束原因决定整组是否强制展开。我们直接按组内是否有失败调用决定：组头只写「有东西失败了」会把批次二刚建立的那行（写着失败原因）重新藏起来，直接违背那次的决定。
- **组在增长时键不变。** 官方用内容派生的组键并在整组连续存在时复用。我们用组内第一个 block 的身份做键，组随 agent 继续工作增长时键不变，所以读者打开过的组不会因为新调用到达而自己合上。

**P4 · 一行就是一行，全文就是全文，没有中间态。** omdsh 原本有第三种形态：带框但输出截到 10 行，末尾挂 `… N more lines · ⟨Ctrl+O: Expand⟩`。折叠之后这条路径不可达（一个 tool block 只在 `toolsExpanded` 为真时才带框），于是整段删除。半截输出是唯一一种读者无法主动阅读的呈现——他无法知道被丢掉的是开头还是结尾。代价是打开一个 5000 行的构建日志会刷屏，由 `windowTranscript` 的窗口裁剪和滚动承担，这与终端里任何长内容的处理一致。

关于折叠层级：官方是"turn 窗口 > step group"两级。omdsh 只做**一级**（turn 边界）——终端只有 35–45 行可用，再嵌一层披露会让读者多记一个层级，而 turn 本来就是他心里的单位（发一条消息、agent 干活、给出回答）。官方那条"回复内容结束过程窗口"的打断规则（`process-groups.ts:159-161`）正好支持一级折叠。

### 五条设计约束（都是被测试逼出来的，不是先想好的）

- **没有档位把三面全展开**。否则 `Ctrl+O` 在那一档无事可做，键位就成了摆设。
- **工作面单调，思考是唯一例外**。`groups`/`tools`/`detail`/`subject` 四个布尔一起动，只有 `reasoning` 独立。这样任一档位里"工作"的疏密是一句话能说完的，思考单独决定。
- **两个安静档必须在最常见场景有别**。`compact` 与 `standard` 若在典型回合下渲染相同，档位就只是名字。
- **计数是事实，短语是散文**。宽度压力下先牺牲短语：`countRoom` 一度限 `room/4`，把 `· 3 calls` 截成 `· 3 …`，改为 `room/2`。
- **成功的调用不带标记**。行槽只留给"在飞"和"出错"；五个 `✔` 排成一行只说明上面的行存在，而它总是存在。

### 有意不做的三件事

- **逐条折叠态持久化**（E9）。与密度抢同一个问题的答案、profile 无界增长、瞬时检视不等于偏好。
- **"全展开"档**。`verbose` 保留思考折叠，否则 `Ctrl+O` 在该档无事可做。
- **照抄 minimax-code 的"无展开三角"**。终端没有 hover，必须有可见的行槽标记。

### 实施中踩到的陷阱

- **宽度探针要按显示格量，不能按 `string.length` 量**。本机（Kaku / `xterm-256color` / `LANG=en_US.UTF-8`）下 `→ · … — ─ │ • ●` 全是 1 格，`中`/`🚀` 是 2 格，宽度表没有 East Asian Ambiguous 类，对本机正确。
- **`∴` 与 `⋆` 的选择只能真机定**。真机 DSR-CPR 探针实测 `∴` 为 1 格、EAW=A；选 `⋆` 之前未测宽度。
- **探针写错两次**：stdout 重定向后 fd 1 非 tty；字符写进文件导致光标未动。两次都表现为"探针没反应"，不是渲染问题。
- **一整行 dim 需要测试钉住"先关 dim 再开 error"**。两种写法在真彩终端上视觉等价，只在 palette 把 error 映射到 dim 色时失败——但那正是读者最需要那个标记跳出来的地方。断言写成字节级序列才抓得住。
- **新增的测试自己也可能抓不住变异**。本批次有三条（首句预览、流式不带 `…`、组头整行 dim）第一版写得太松，换回旧实现照样全绿；逐条反向验证后重写才真正有约束力。**每个新测试都要先变异一次再算数。**

## 批次九：按回合折叠，对齐 Web（已实施）

批次七让思考「像回复一样结束一段过程」，本意是不让思考被藏起来。用真实会话回放（85 次调用、52 段思考的一回合）检验后发现它让折叠整体失效：模型几乎每一步都思考，一回合被切成约 40 段，standard 档仍有 161 行，组头 `Ran commands · 2 calls` 重复二十次。批次九推翻这一条，改为与 DSH Web 一致的形状：

- **思考是过程的一员**。`isProcessBlock` 接受只有思考的 assistant 块；只有用户消息、回答正文、改动文件记录结束一段过程。回答块自带的思考由 `ProcessGroup.absorbs` 收进组里作为最后一行，回答正文仍在组外渲染（`omitReasoning`），不改 block 列表。
- **一行一个格式**：`标记  类别 · 对象`。思考是 `∴  Thought · 首个有信息的句子`，调用是 `•  Run command · 描述`。bash 优先用 `description`（Web 同样如此）。成功调用只保留 diff 的 `+N -M`，行数与 `exit 0` 去掉。`•` 占住标记列，否则展开的思考正文与下一行调用的标签落在同一列、读成一段。
- **组头带回合耗时**：`turn/start`→`turn/end` 的日志时间记入 `TranscriptState.turnSpans`，只有回合的最后一段过程写 `Worked for 13m 36s`。进行中写 `Working`，不写时间（P1 仍成立：时钟归状态栏）。
- **进行中只画最新 5 行**（`LIVE_GROUP_ROWS`，已在批次十二撤销，见下文）。进入原生 scrollback 的行不可改写，完整画出的进行中列表会永久留在历史里；尾窗让历史留下的就是折叠后的样子。回合仍在跑时，末尾那段过程在两次事件之间也算进行中，否则会闪烁开合。
- **失败不再展开整组**。组头标 `✘ N`，组头下只露出失败的那几行。长回合里一次 `grep` 无匹配就展开五十步，是最常见的失败把折叠整体撤销。
- **预览跳过填充句**（`Good.`、`Hmm.`、`Now,`），句末引号随句子一起取，CJK 句号不要求后随空格。

验证：8 处反向变异（思考不入组、无尾窗、失败展开、无填充跳过、无耗时、无吸收、无闭合引号、无末段进行中）均有测试失败。

## 批次十：一个回合一段过程，一套网格（已实施）

批次九之后真机截图仍然显得零乱。逐项定位后，原因不在单行措辞，而在四条左边界和回合被再次切碎：

- **回合才是折叠单位**。批次九仍以「两段回答之间」为界，于是模型中途写给用户的话（「我在，已就绪。」）和回合中完成的后台任务通知又把回合切成几段。现在一段过程是同一回合里从提示词到最终回答之间的一切，包括中途回复（展开时按原样 markdown 呈现）和过程型通知（`Block.notice.process`，仅在回合进行中产生）。回合号记在工具块上（取自 `tool/call` 的 `turn`，回放与实时一致），没有提示词隔开的两个回合（如 goal 续跑）仍是两段。最终回答流式输出期间，这段过程保持展开，回合结束才折叠，避免开合闪烁。
- **一套网格**。标记占第 0 列加一个空格，所有块的文字从第 2 列开始：回答（`ASSISTANT_PADDING_X` 由 1 改为 2）、提示词、组头、通知。组内缩进 2，标记在第 2 列、文字在第 4 列。此前同屏有第 1、2、3 列三四条左边界。
- **事实跟在句子后面**。失败原因不再右对齐到行尾，而是 `✘ Read file · AGENTS.md · cannot read …`；组头的失败写成句尾的 `✘ 1 failed`，窄屏先丢 `Working`、再缩成 `✘ 1`，调用数始终保留。
- **提示词是一整块色块**，上下留白行同色；此前留白行不着色，与块间空行叠成两行空白。
- **代码块用竖线**，不再打印 ``` 围栏；折行的每一行都带竖线。

验证：7 处反向变异（中途回复切组、不按回合切、通知切组、窄屏不让位、留白不着色、事实右对齐、旧边距）与 provider 层通知接线的两种变异均有测试失败。

## 批次十一：展开不改动流（已实施）

真机上「进行中展开再收起」会让屏幕只剩输入框下边和状态栏，回合结束后展开再收起会让回答末段在历史里出现两次。根因是同一个：渲染器用行号记录已冻结进终端历史的边界，而原地展开或收起会让边界之后的行整体移位；终端历史只能追加、不能回收，于是变短时要么留白、要么把已冻结的行再画一遍，变长时会把已在历史里的行再推一次。

渲染器侧的修补（`reflow(fromRow)`：变形起点在边界之上时只重画屏幕、不写历史）只能在「留白」和「重复」之间选一个。真正的解法是不让读者的操作改动流：

- **Ctrl+O 进入检视**：打开视口下的过程、调用或思考，视图移到它并在浏览帧（与 PgUp 同一条不写历史的通道）里展开；再按 Ctrl+O 或向下滚过末尾，结束检视、清除所有展开、回到跟随。检视期间即使内容放得下一屏，也不自动恢复跟随，否则打开的内容会回到流里。
- **进行中的过程不冻结**：只要回合在跑，最早一段进行中过程的组头就是 `liveStart`，并置 `livePinned`；尾窗滚动、回合结束时折叠都发生在可变区域，回合结束后以折叠后的形态一次写入历史。
- **折叠形状签名**：渲染层给出每个打开面的键与行（`foldMarks`），provider 比较前后两帧取最早变化的行调用 `reflow`，覆盖切换档位等仍会在流里改形的情况。
- **Ctrl+O 的目标**：回合结束后跟随尾部的锚点落在回答之后的改动文件记录上，曾退化为「全部展开」；现在越过回答与其后的记录仍命中该回合的过程。按键前若有合并中的待渲染帧，先渲染再取锚点。

验证：带滚动与历史缓冲的假终端上，端到端测试覆盖进行中打开再关闭、回合结束后打开再关闭（屏幕与历史逐行不变）、打开最后一段过程、只打开该回合而非全部调用、进行中过程不进历史。反向变异中「进行中不固定」「锚点不越过回答」「按键不先渲染」「检视中 Ctrl+O 不结束检视」「渲染器不 reflow」均有测试失败；「检视中内容放得下时恢复跟随」一条在现有场景里被 `reflow` 兜住，没有单独失败的测试，作为纵深防御保留。

## 批次十二：进行中不成组（已实施）

对照 DSH Web 运行中与结束后的截图：Web 在回合进行中不建组，思考、调用、中途回复按顺序平铺，中途回复就是普通正文；回合结束才收成「已完成，用时 N 秒」并折叠。omdsh 此前在回合开始就套上 `▾ Working` 组头并只画最新 5 行，中途回复一被挤出尾窗就看不见，读者感觉「正文被盖掉」。

- **进行中不画组头、不截断**：`turnGroups(state)` 在 `processGroups` 之上把正在运行的回合末尾那段标为 live（两次事件之间、最终回答流式输出期间也算），live 段按平铺列表渲染在正文边距上，不缩进；`LIVE_GROUP_ROWS` 删除。
- **结束后才成组**：回合结束时这段过程第一次出现组头 `▸ Worked for …`，并以折叠形态写入历史（仍由 `livePinned` 保证进行中不冻结）。
- **组内不重画回答**：吸收进组的回答步只画其思考行，正文只在组外出现一次（此前展开时组内外各一次）。
- **Ctrl+O 与渲染同源**：provider 用同一个 `turnGroups` 取目标，live 段不是组，按键落到视口下的调用或思考上。

验证：真实会话回放中进行中无组头、历史不含任何过程行、最后一句话只出现一次；反向变异「进行中画组头」「进行中缩进」「回答流式时折叠」「从不 live」均有测试失败。

## 批次十三：分界线只说明文档切换（已实施）

## 批次十四：从最新内容开始展开，滚轮浏览（已实施）

## 批次十八：收缩后的冻结边界（已实施）

reflow 收缩后直接采用 viewport 起点，会把已经进入原生历史的行重新视为未提交；后续增长因此重复提交这些行。除合成 renderer 序列外，真实 LocalTui 在长回合结束后从 verbose 切到 standard、再开始下一回合也可复现，第一回合的用户提示在历史里出现两次。

冻结边界表示当前文档的逻辑行索引，不能用旧计数直接 clamp。renderer 保留最后一个跟随帧的已格式化行引用，用未改变的前缀与后缀映射边界；生产帧复用现有 blockStarts 按同一文档中的块定位，避免浏览期间追加的新回合被当作重排范围。比较范围排除实时页脚。收缩把已冻结行带回视口时，这些行可以重绘，但不再进入历史；重复重绘、reset 和覆盖层返回都保留这一状态，直到新内容越过冻结边界。普通绘制和滚动不执行重排比较，也不重新格式化历史。

renderer 测试新增完整 scrollback 断言，覆盖收缩后增长、重复重绘、reset、浏览返回、回答后缀与页脚同时变化。真实 LocalTui 测试覆盖有色与无色、直接跟随与浏览期间切换密度，并断言旧历史前缀不变、旧提示只提交一次、后续回答进入历史且尾部可见。五项反向变异全部被捕获：退回 viewport 边界、直接 clamp 旧计数、丢失冻结行的视口状态、把实时页脚纳入比较、忽略块对应关系。

## 复查修掉的三处回归（已实施）

批次九到十八的实现引入了三处缺陷，都由 review 与反向变异发现，而不是由当时的测试发现。三处都曾让一个本该可见的东西消失或错位，因此按「读者先看到什么」重新定位。

**回答整段消失。** run 的回答原本取自段的**最后一个**块，而批次十引入的 `Block.notice.process` 恰好让工作可以在回答之后落定：`tool → 最终回答 → 后台任务通知 → turn/end` 是合法顺序，此时段尾是通知，代码判定「这段没有回答」，于是把回答本身折进了 run。standard 密度下整个回复从屏幕上消失。回答改为**扫描整段取最后一个有正文的 assistant**：中途回复归 run，最后一条才是结论。`ProcessGroup` 因此多了一个 `answer`（结论所在）与 `until`（整段终点，含落在答案之后的工作），两者分开是因为「run 的成员」和「这一段的全部块」不是同一个边界——混用会让遍历重新进入同一个 run、重复画组头。

**缓存键漏掉 `state.status`。** `turnGroups` 新增了对 `state.status` 的依赖（进行中的回合平铺、结束后才成组），而 `renderTranscriptBody` 的缓存键以 block 数组为索引、`status` 在数组之外。`setStatus` 只改 `status`、保持 block 身份，于是第二次状态切换直接复用第一次的行：先 idle 后 running，进行中的回合带着已折叠的形状回来；先 running 后 idle，已结束的回合不再成组，丢掉组头与耗时。缓存键补上 `status` 与 `focusBlock`。

**通知开头的 run 撞 key。** run 以首块为键，而过程通知的首块身份此前退化成裸 kind，于是**每一段以通知开头的 run 共用一个键**；`openedGroups` 是 `Set<string>`，打开一段会打开全部同类段落，方案里「读者打开过的组不会自己合上」这条不变量失效。通知改用它的持久标识（retry 的 `retryId`、后台任务的 job id）参与键，无标识的旧日志退回按位置取值。

三处各有一条反向验证：退回「只认段尾」→ 2 个测试红；缓存键去掉 `status`/`focusBlock` → 2 个测试红；`blockIdentity` 退回裸 kind → 1 个测试红。修复过程中另有两处自身缺陷由测试逼出并修掉：run 的 `groupOf` 覆盖到 `until` 却仍按 `end` 推进遍历，导致重复进入同一 run 直至栈溢出；被吸收的答案块一度拿不到行偏移，使 `focusBlock` 落到别的块上。

第二轮复核又找出四处，其中三处是上面那次修复自己引入的：

- **行偏移按绘制顺序 push，而 `blockStarts` 按块下标索引。** 一旦一段 run 带有答案、答案之后还有工作，绘制顺序与块顺序就不一致，正文与通知拿到了对方的行：搜索命中正文跳到通知，`Ctrl+O` 瞄准错误的 run。偏移改为**按下标赋值**，并让 run 按事件顺序绘制（run 的工作、答案、其后落定的工作）。
- **答案绕过了通用渲染路径**，直接调 `blockLines`：正文里的搜索命中不再反白，且每次重算都重新排一遍 Markdown。答案改走 `cachedBlockLines` 与同一条高亮路径。
- **run 统计只数到答案为止**：落在答案之后的调用不计入 `calls`/`failures`，组头因此少报调用数、并漏掉其后的失败。统计改为覆盖整段。
- **`retryId` 不是重试通知的唯一标识**：上游在一条重试链上复用同一个 id（`dsh-llm-retry/lib/index.js:166`），链被别的通知打断时两段会撞键。source 改为 `${retryId}:${retry}`。

顺带按复核意见收敛了数据结构：`answer` 取代原先的 `end` 推导，`absorbs` 换成一个布尔 `tookThought`（那块永远是 `answer`，不需要第二个下标），`until` 的注释与实现对齐——答案之后落定的工作同样计入组头、并按事件顺序画在答案之后。

`smoke-fix.spec.ts` 里另有一处自身错误：工具调用的 `turn` 被写死为 1，第二段的工具并不属于第二段，一并修正。

第三轮复核推翻了第二轮「按事件顺序绘制即可保证偏移单调」的判断，并要求先补失败测试再改冻结边界。实测确认：折叠的一段 `[tool(error), tool(ok), answer]` 的偏移是 `[header+1, header, answerRow]`——**非单调**。原因不是本轮引入，而是折叠的段只给失败成员正文偏移，未显示的成员一律落到组头。搜索与 focus 靠偏移定位行，而 `#reshapedBoundary` 用相邻块推算跨度，因此这条路径值得单独立一个测试；本轮只记录，未改实现。

- **宽度变化的 resize 会解开已冻结的行。** 收缩一段 run 后冻结边界被映射到新行空间，位置可能高于视口起点；此时一次**只改宽度、不改高度**的 resize 采信视口起点作边界，忘记终端已持有的行，后续增长把旧行再提交一次（`head-8` 在历史里出现两次）。现在只有**高度**变化才重新推导边界——高度变了终端自己搬过行；宽度变化不搬行，映射过的边界必须保留。已在收缩→resize→增长、浏览期间 resize→返回、真实高度变化三条路径上补测试。
- **搜索命中被吸收的思考时，命中位置看不到。** run 把回答那一步的思考收作最后一行、只留正文在外，命中落在预览之外时命中被报出、却没有任何一行通向它。现在命中思考会把该思考整段展开并对准。这一条是渲染决定而非读者自己的状态，因此走一个局部集合，不写进宿主传入的 `expandedReasoning`。

新增测试同样逐条反向验证：还原 resize 的旧边界 → 红；去掉「命中即展开思考」→ 红。过程中两次写出抓不住目标的断言（只断言整帧出现任一反白、以及断言一个并不存在的标签行），改为断言**正文所在那一行**与**标签下一行的完整思考**后才真正有约束力。

第四轮复核指出上一轮的 resize 修复只闭合了直接跟随这一条路径，**浏览返回仍是原缺陷**：overlay/浏览返回的分支（`main-screen-renderer.ts` 的 `#adoptPhysicalAfterTransient`）同样无条件把冻结边界重置为视口起点。上一轮的测试之所以通过，是因为它把 reflow 留到返回时才处理，走进了 reflow 分支而不是 resize 分支——测试顺序掩盖了它。改为「先跟随完成收缩与映射 → 再浏览 → 只改宽度 resize → 返回且无待处理 reflow → 增长」，`head-8/9/10` 再次出现两次，缺陷复现，随后按同样的「高度变化才重新推导」规则修好。

同轮还修正了一处**判定口径**：`oldHeight !== height` 表示净高度变化，而 10→8→10 这样的抖动净变化为零、终端却真的搬过行。`ResizeTransition` 增加 `heightMoved`，记录本次 resize 突发中是否发生过任何高度变化；并补了 10→8→10 的测试。

搜索定位也补完：命中落在被吸收的思考里时，偏移指向**思考所在行**而非下方正文，否则长思考的命中停在视口上方。偏移仍是块级的——`transcriptSearch.matches` 是块下标，滚动到块首行是既有契约，本轮没有改成行级，这一点在测试里按块级契约断言。

`end` 与 `answer` 的冗余：复核指出当前 `end = memberEnd = answer ?? until`，我上轮说「三者不能互推」与工作区不符。属实——这条冗余属实但无行为影响，留待与折叠段非单调那条一并处理。

第五轮复核指出第四轮的高度修复**仍未闭合**，而我用来验证它的两条测试是**假的**：`Emulator` 原本是定高的，没有 `resize`，所谓「终端真的搬了行」从未发生，断言只看历史前缀——末尾追加旧行照样满足。给 `Emulator` 加上真实的 `resize`（变矮推入 scrollback、变高拉回）之后，两条测试立刻变红：旧 head 行被重复提交。

同时纠正了判定口径：高度变化**不是**把逻辑冻结范围重置的充分条件。reflow 已经把边界放在当前文档的行空间里，终端的搬行是屏幕层事件；把边界降回视口起点，等于把剩下的冻结 head 交给下一次 flush。现在的规则是——映射过的边界存活，并按终端**实际收回的行数**上移（变高拉回几行就上移几行）；从未映射过的边界仍取视口起点。上一轮引入的 `heightMoved` 在此证明只是「换名的 sticky heightChanged」，已删除。10→8→10（无中间 paint）与真实变高两条路径现在都接了 `emu.resize`，并断言旧行**次数为 1**，而不只是历史前缀。

折叠段非单调的 mapper 测试按复核要求补上（失败→成功、成功→失败→成功两种形状，带真实 `blockStarts`，开合后追加）：**当前 mapper 两条都绿**，因此按「绿就保留实现」未改 `reshapedBoundary`。但必须说明这两条测试**没有钉住 mapper 的选择规则**——扰动它的 `findLastIndex` 仍然全绿，因为夹具各块跨度过于均匀，任意相邻一对都映射到同一边界。要钉住需要一个各块跨度明显不同的文档，那是夹具工作而非契约变更；测试里已把这个限制写明，不谎称覆盖。

overlay 往返：复核指出 alt 与非 alt 两条路径应同样保留冻结边界。实测 alt 路径的**历史**已经正确（两条都绿），因此没有改实现。中途我曾让 overlay 保留待处理的 resize，但反向变异证明那条改动不承重（去掉后测试仍全绿），已**撤回**——不留下无法验证的代码。alt 分支上多留一屏行是模拟器 alt-screen 模型的限制，不是产品行为，测试按此收窄。

第六轮复核发现两处**我自己的测试是假的**，都属于同一类错误：断言写得像在验证某件事，实际验证的是别的东西。

**`Emulator` 早就有 `resize`。** 我上一轮以为它没有，于是又加了一个——类里因此有两个 `resize`，JS 后定义覆盖先定义，我新写的那个实际上**顶替**了原有的、行为不同的那个。复核要求先去掉重复方法并核实门禁结果对应的是哪个文件，这一点完全正确。现已删除多余实现，恢复到原有的真实 `resize`。`ResizeTransition` 里那个换名的 `heightMoved` 也确实还在（我早前以为已删），现已删除。

**变高后的重放：静态反例在本代码上不成立。** 复核给出的反例是 height10→14 拉回后 `physical` 降至 11、追加 9 行使 `candidate` 越过它、于是 `flush[11,13)` 重复提交 `head-11` 与 `run header`。按此把文档拉长到增长真正越过该边界、并断言「历史中任一被冻结的行都不得再次提交」后，测试**全绿**：实测 `RESUB []`。原因是 `#paintFlush` 的区间判断先于这次提交，冻结行不会被再次送出。因此变高按实际收回行数上移的规则虽然保留，但它的价值不在于避免这次重放，而在于不让边界被丢弃。当前实现保留、未改，测试按真实结果断言。

**mapper 夹具此前是无效的。** `offsetsFor` 写出的两行尾部 `[12,12,12,17]` 与 `[12,12,13,17]` **都是单调的**，根本没有复核要求的 `[13,12]` 下降；`withFailure` 的参数从未被使用；而 opened 与 closed 的块身份已经错位，破坏了 mapper 的前提。已改为**从真实 `renderView` 取 `blockStarts`**，并加一条断言 `expect(monotonic).toBe(false)` 确认这个夹具**真的**非单调——没有这条，上面两条等于什么都没测。

即便如此，mapper 的**选择规则**仍未被钉住：扰动 `findLastIndex` 的阈值仍然全绿，因为本夹具里边界远低于每个成员的起点，平移阈值选到同一块。要区分，需要复核给出的形状——边界落在**某个成员跨度内部**（已冻结的长回答中段，上方 run 展开）。这条夹具是下一件要写的事，未完成前不宣称覆盖了选择规则。

第七轮复核指出：上一轮「变高重放不成立」的结论是我**又一次把断言切片起点选错**造成的假阴性。`slice(afterShrink.length)` 从 36 起，但 resize 已经把历史从 36 条缩到 32 条——恰好跳过了随后被重复提交的那四条。改为从 resize 之后的实际长度起算，并直接断言 `head-11`/`run header`/`run-row-0`/`run-row-1` 四个唯一标记的历史次数后，**缺陷立即复现**。

根因与我上一轮的方向判断相反：变高拉回的是**边界之下**的未冻结行（它们本来就没冻结），边界根本不该动。我当时写的「按实际收回行数上移」恰恰把已冻结的 11–14 行解冻了，于是下一次 flush 又把它们送进历史。现在的规则是**更简单的那个**：高度变化完全不移动边界，只做文档范围钳制；未映射过的边界才取视口起点。反向变异（改回 `viewStart`）→ 4 条测试红。

同轮指出的浏览返回分支同样仍是 `moved → viewStart` 解冻，也已按同一规则修好，并补了「浏览期间变高 → 返回 → 增长跨过边界」的测试（反向变异 → 2 条红）。简化后 `#frozenHeight` 与 `heightMoved` 都成了死代码，已删除。

mapper 夹具按复核要求重写：同一份 blocks、只切 `openedGroups`，并断言 `open.lines !== closed.lines` 且答案的绝对起点确实下移——此前的 `framesFor` 没传 `openedGroups`，open 仍是折叠帧，mapper 在 prefix 分支就返回了。现在夹具真的产生 `[0,4,5,4,7]` 这样带下降的偏移。但这一条只覆盖 scrollback 不变式，**仍未钉住选块规则**：`Math.max(candidatePhysical, mapped)` 之下，本夹具里视口起点已越过映射值，错误选择被掩盖。

第八轮复核纠正了我对该限制的**过度概括**：`max()` 只在「正确结果与被扰动结果都 ≤ candidatePhysical」时不可区分；若错误映射更大，仍会过度冻结、漏提交。复核同时纠正了它自己先前的夹具建议——只加长答案不够：run 展开 Δ 行而高度与后缀不变时，`mapped = P+Δ` 而 `candidate = P+Δ`，**恰好相等**，没有差距。

按它给的形状补了「哪一段跨度被选中」这条：冻结长回答的前 6 个显示行 → 窗口变高 4 行（视口起点下移而文档不动，造出 gap=4）→ 同一 blocks 只开 run（答案下移 24 > 4）→ 增长跨过映射值。**两类变异现在都会被捕获**：`findLastIndex` 换成固定索引 0、以及阈值平移 6，两条都红。这条夹具不需要猜文档长度。

同轮还发现 resize 分支**优先于** reflow 分支，且同帧会清掉 `reflowFrom` 并记录新的 `followRows`，于是 resize+reshape 同帧时映射完全丢失——表现为**漏新尾**而非重复（`new-0`/`new-1` 从未进入历史），只查旧行次数抓不到。现在 resize 分支自己完成待处理 reflow 的映射并消费掉它，反向变异 → 1 条红。

另外把「变高拉回的是从未冻结的行」这句解释改掉了：它拉回的是**旧形状下进入历史的快照**，不对应当前文档行；保留文档冻结边界的修法是对的，但不依赖那个解释。

第九轮复核给出 resize 契约的最后一个具体漏尾：**仅宽度 resize 与普通新内容增长同帧**。没有 reshape，文档只是变长；resize 分支走「采信视口」那条路，短文档下视口起点已越过旧边界，于是两者之间的行既没提交也不在屏上，之后再也不会补交。静态反例复现：`new-0`…`new-21` 从未进入历史。关键区分是——**这帧首次到达的新文档行**与**终端几何已经自然搬过的旧屏行**不是一回事，不能统一提升到 candidate 就当已提交。现在宽度变化且文档增长时按普通 flush 提交这段（高度变化不走这条，终端自己搬过行），反向变异 → 红。

同时按复核要求把选择规则夹具的切片起点从 resize 前的长度改为**增长前的实际长度**（变高已把历史缩短，原起点会跳过恰好是错误映射落点的那几行），并补上**正向**断言：提交要从已冻结段之后继续、中间不丢——此前全是「没有重复」的断言，映射到答案尾部或过度冻结都可能全绿。两类变异（选第一块、阈值平移）被捕获；「永远选最后一块」仍通过——复核纠正了我对此的解释：并非两者描述同一跨度，而是本夹具里最后块与答案恰好具有同样位移，公式外推到该跨度之外也算出了同一个值；要区分需要两处**不同的局部变形**（例如上方 run 展开而答案下方另一 run 收缩）。这条未覆盖已按原样记录，不为它再拖延形状通知。

第十轮复核指出**上一轮的修法本身引入了新回归**，而且不需要文档同时增长就能复现：`widthChanged` 不等于「仅宽度」。resize 同时改宽高时终端已经自己把行推上去了，按 flush 再提交一次就是重复（`a,b,c,d` → `a,b,c,d,c,d`）。已加该反例测试，条件改为「高度确实未变」。

但复核同时指出：**仅仅把该 flush 禁用于高度变化，并不等于这条路径已解决**。终端只提交了它自己搬走的那几行；同帧首次到达的新行从未被任何东西搬过，若直接采信视口起点就会跳过它们。现在按「终端搬走多少行」计算 flush 起点：变矮 N 行就从旧边界 + N 起提交，跳过终端已提交的、提交本帧新到达的。两条测试（仅宽度+增长、高度+增长）各自锁住一个方向，反向变异 → 4 条红。

过程中我又一次把断言写错：以为「变高 2 行」意味着历史多 2 条，实际终端的 resize 与 painter 的时序使结果不同；改成断言真正的不变式（已有历史原样在前、无内容行重复、`head-8`/`head-9`/`new-0`/`new-23` 各一次）后才通过。

复核还指出一处**比较口径不一致**：选择规则夹具里用带 padding 的原始行建 `Set`、却用 trim 后的行去查询，永远匹配不上、断言形同虚设。现已统一为 trim 口径（空白行本就重复，按内容判重）。它也指出 `answer line 0` 属于已有历史、单独 `contains` 不证明新增提交——这条接受，但保留，因为它与 `answer line 3` 一起表达了「从已冻结段之后继续」。

关于搜索形状通知，采纳它的建议：mark key 沿用既有的 `thought:${reasoningKey(member)}`，不因搜索目标变成两种状态——思考有效展开时该键存在、收起时不存在，宿主展开与搜索派生展开共用同一键，不把 query 或展开原因编码进去；正文始终画出，无需新 mark。row 取思考真正起点，即 `bodyRow + body.offsets.get(answer)`，且必须在正文覆盖 offsets 之前保存。

第十一轮复核证明我上一轮的 `from = physical + moved` **公式本身不成立**：它只在「旧屏顶部恰好对应冻结边界、且被搬走的行在新文档里仍是连续旧正文」时正确。reflow 之后 `frozenViewport` 刻意让旧屏顶部 `S` 低于边界 `physical`，恰好破坏这个前提。反例复现：`physical=15`、旧屏显示 `[8,18)`，终端缩 2 行搬走的是逻辑 `[8,10)` 而不是 `[15,17)`，而公式算出的 `from=17` 把 `answer`(15) 与 `new-0`(16) 一起跳过了。

改法不是再换一条加减式，而是**分别追踪两个不同的量**：终端提交的是**上一帧屏幕的顶部** `#screenTop`，不是文档边界；flush 从 `#screenTop + 高度差` 起算。该帧 `#screenTop` 随 `effectiveStart` 记录。两种反向变异（退回 `physical + moved`、去掉高度偏移）各自被测试捕获。复核提醒不要把它变成另一条万能公式——需要时仍要能推出实际旧屏行的来源，这一条已写进注释。

同轮补了 10→8→10 净零突发 + 增长的用例。复核判断净差为 0 是对的（推入的两行随后从历史尾部拉回，最终状态复原），实现也确实如此；新增长行照常提交，无重复。这里我又一次把断言写错：拿带 padding 的行与 trim 后的行比较、并把仍在屏上的尾行 `new-19` 当作必须进历史。改成比较 trim 口径、只断言确实首次到达的前几行。

关于顺序，复核要求**先写假终端行为测试再补 marks**，且不要在测试里无条件调用 `reflow`（那会掩盖最初缺通知的问题）；行为用例应经过真实 provider 的 `foldShape` 比较/通知，shape 字符串测试只作定位与宿主集合不变的补充。它还指出一个本轮实现必须验证的风险：`blockStarts[answer]` 会随命中位置在思考起点与正文起点之间切换，而 mapper 把它当同一块的几何锚点——加 mark key 只触发通知，不会让 mapper 自动改用两个锚点。

第十二轮复核指出第十一轮的修法**丢掉了冻结边界这个下限**。用屏幕来源替换边界之后，flush 从 10 提交而不是 15：`answer`/`new-0` 补回来了，但 `head-10`…`run-row-1` 这些**早已冻结**的行又被送进历史（`head-10` 出现两次）。我上一轮的测试只查 `answer`/`new-0` 各一次，恰好查不到重放。现在起点取**两者的较大值**：`min(candidate, max(physical, screenTop + 高度差))` —— 屏顶说明终端自己提交了什么，冻结边界说明更早的帧提交了什么，二者缺一不可；只用屏顶会重放，只用边界会漏掉终端没搬的那些。

同轮两处也都成立。**`effectiveStart` 并不隐含排除填充行**：`#target` 另有 `offset`，短文档的物理屏顶部可能是空白，终端缩屏推上去的是空白而非内容行，把它当成「已提交的内容」就会跳过真正的行。已记录 `#screenPad`（上一帧内容之上的空白行数），并从「终端推走多少」里扣除——被推走的空白不是被提交��文档行。**browse 帧不经过 `paintFollow`，`#screenTop` 因此失真**：浏览中终端缩屏推走 `head-0/head-1`，而返回帧仍按旧屏顶算起点，把 `head-8`/`head-9` 跳过（既没自然入历史、也不在最终视口）。现在浏览帧也记录其文档窗口起点与偏移。

三处各自有测试锁定，`physical` 下限、去 padding、browse 记录三种反向变异分别变红。复核同时提醒不能笼统在 `paintTransient` 记 0、也不能等 adopt 才重置——返回帧在 adopt 前就可能用 resize 分支的旧值；当前实现只在**主屏**（`surface === 'scroll'` 且非离开 alternate）时记录，alt 的行属于另一缓冲区，不覆盖主屏来源。这条规则写在代码注释里。

至此 resize 契约有 12 条测试，全部反向验证：同帧 resize+reshape、宽度+增长、宽度+高度（终端已搬）、高度+增长、高度+增长且边界高于屏顶、冻结下限、padding 顶部、净零突发+增长、跟随变高、browse 中变高后返回、browse 记录屏顶、宽度 resize。复核指出的「9 条测试并未证明无漏尾且无重放同时成立」是对的——现在两种方向各有独立断言。

第十三轮复核指出「屏幕来源」不是 `top + pad` 能表达的，并给出三条同源反例。**第一条成立且我上一轮的修法是假的**：`#paintTransient` 调的是 `#target(next, 0, 'top')`，切片已由宿主窗口化，所以 `0` 是**窗口内**位置而非文档行号；我记录的 `target.start` 恒为 0，而我上一轮的 browse 夹具恰好 `slice(0, 10)`，硬编码 0 也会绿。非零 browse 反例复现（浏览 `slice(8,18)` 后 resize，`head-8` 两次）。现已把宿主上报的 `transcript.start` 作为文档窗口起点传入。

**另两条我没能修好，因此没有留下会红的测试。**

- **主屏 overlay 的推行行不可计入正文。** overlay 覆盖主屏时，终端推走的是 overlay 的行，与文档无关；当前把屏顶按 overlay 之前那个 follow 帧计算，跳过了 `head-8`/`head-9`（既未自然入历史、也不在最终视口）。
- **被新正文顶替位置的推行行不可计入。** 旧 composer 的逻辑位置被新行占据，它进入历史不等于该位置的新行也已提交；当前按「推走行数减去前置 padding」计算，会跳过 `new-0`。

我试过两种改法（按屏幕行内容逐一比对、只从首个内容行起算），两者都在另两条已通过的用例上回归——`#screenPad` 在短文档下是 0 而实际内容从第 2 行开始，前置 padding 不能从 `target.offset` 直接得到。反复试错已超出合理范围，因此**撤回本轮未验证的改动**。当前保留的是第十二轮验证过的规则（`min(candidate, max(physical, screenTop + 高度差 - padding))`），resize 线就此**不算完全闭合**。

这两条以 `describe.skip` 保留在 `main-screen-renderer.spec.ts`（`known resize-source defects, not yet fixed`），**不是删除**——失败的输入必须留在仓库里，否则下一次改动会以为这里已经解决。

### 让帧说明它画的是哪一段文档行

上面两条缺陷同源，根因是渲染层靠「顶部行 + 空白行数」去猜终端搬走的是哪些**文档行**。现在帧自己说：

```ts
interface DocumentRows {
  documentStart: number   // 半开区间，与 physical 同一坐标系（含 welcome 前缀的绝对行）
  documentEnd: number
  frameStart: number      // 在 Frame.lines 中的起点
}
Frame.documentRows?: DocumentRows | null
```

**三种状态必须分开**，这是这次修复里最容易做错的地方：

- **对象** = 已知正文区间。
- **`null`** = 这一帧确实没画正文（全屏界面、主屏 overlay、只剩溢出指示行的窗口）。
- **省略** = **来源未知**。这是信息的缺口，不是答案；渲染层不得把它当成「没有正文」而清掉记录，也不得拿上一帧的区间替这一帧抵扣。

`windowTranscript` 报它输出的窗口来自哪一段、起点在输出里的位置（顶部 ↑ 标记时 `frameStart = 1`；预算只剩指示行时给 `null`）；`renderView` 换算到最终 `Frame.lines` 坐标；agentHub、trajectory、settings、fullscreen-list、plan-review 五处提前返回都给 `null`。**不按 `transientSurface` 一刀切**——内联覆盖层可能仍画出正文，按实际 `Frame.lines` 报来源。

渲染层按缓冲区规则更新记录：主屏画对象就保存经 `target.start`/`offset` 裁剪后的区间；主屏画 `null` 就清掉旧来源（overlay 推走的行不抵扣正文提交）；主屏画未知就使旧来源失效；**alt 画任何帧都保留主屏记录**，因为那是另一个缓冲区，`null` 描述的是 alt 帧。

提交时按**区间差集**处理，不是换一个上界数。冻结边界是**下限**（更早的帧已提交过其上的一切）；终端自己搬走的是**另一段区间**，且它不必与下限相接——浏览窗口从边界之后开始时，终端提交的 `[20,22)` 与冻结边界 8 之间留下一段谁都没提交的空洞，单个 `max` 会把整段丢掉。所以真正提交的是 `[floor, candidate)` **减去**终端提交的那一段，可能分成两半。两半必须**一次画出**：`paintFlush` 每次都以清屏开头，分两次画第二遍会抹掉第一遍，所以新增了 `paintFlushRanges`。

抵扣的三个要点，每一个此前都错过：

- **窗口没提交任何行时必须说"没有"，不能报它的首行。** 返回 `source.start` 会让 `[8,12)` 被跳过。
- **推走的行里不是文档行的要跳过，不是终止。** 顶部 padding 或 ↑ 标记都不对应文档行，终端推走「标记 + 它下面第一条正文」时，那条正文确实进了历史，在标记处停下会把它漏掉。
- **逐行核对文档在该位置是否仍是同一行，而且**前导空白算内容。** `'    a'` 与 `'a'` 是不同的文本，给代码加缩进正是这么发生的；两侧都 `trim()` 会把它们判成同一行，于是顶替它的新行被当成已提交、它下面的行从未提交。右侧填充要归一化——行按帧宽补齐，那部分跟随终端而不是文档。

抵扣出来的**顺序不是文档顺序**，这一点已写进测试而不是含糊过去：浏览窗口的顶行先被终端自然推入历史，冻结边界与窗口之间那段空洞由差集补交，于是原生历史的实际顺序是「已冻结的前缀 → 窗口顶行 → 空洞 → 其余」。历史只能追加，事后差集无法把前段插回去。**原生历史是「当时屏幕上是什么」的快照，不是当前文档的有序前缀**——这正是整套冻结边界工作的契约基础。若产品要求历史严格等于文档顺序，只有在终端自然推行发生之前解决这一条，事后补交做不到。

三条反向变异分别锁住：跟随帧报"无正文"、抵扣退回单个 `max`、非文档行改成 `break`。另有一条锁住 `trim` 归一化。

仍未验证：alt 缓冲与主屏交错时，隐藏主屏上的 resize 搬行行为。现有假终端忽略 `h`/`l`，只支持静态判断，不足以证明这一点；1049 双缓冲模型作为独立项后排。

### run 边界的字段收敛

`ProcessGroup` 原本同时有 `end`（成员终点）、`until`（整段终点）与 `answer`（结论位置），而 `end` 恒等于 `answer ?? until`——两个可推导的量并排放着，就要有人保证它们不漂移。现在只留 `start` / `until` / `answer` / `tookThought`，成员终点在需要处按 `answer ?? until` 读。`until` 继续作为整段推进终点：它之后落定的工作照旧计入组头、照旧画在答案之后，不会漏出统计也不会被重复绘制。

验收看的是「答案之后的工作既不漏统计也不重画」这两条仍在，字段数量不是验收标准。

### 已知缺口（复核明确指出，非穷尽认证）

不凭轮次数认定覆盖穷尽。复核逐行读出并确认的剩余缺口有四项：

1. **`turnSpans` 缓存键**——实现里比较 `cached.turnSpans === state.turnSpans`，而回合结算会换掉这个对象、**不换任何 block**，所以不比较它就会永远画着旧时长。已补两条回归（同一 blocks 从「无 elapsed」到「2m 5s」，以及时长本身从 1m 改到 10m），反向变异（删掉该键比较）→ 两条红。原有的耗时输出测试走的是**格式化**路径，不等于缓存复用路径，所以不能替代。
2. **mapper 选块规则**——已把几何映射抽成纯函数 `mapBlockSpan` 并直接测返回值，用一组不需要调长度的偏移（`oldStarts=[0,10,30,50]`、`newStarts=[0,20,40,45]`、`physical=16`）：正确选择返回 26，而「永远选最后一块」会算出 11。两种选择（末块、首块）都被这组用例杀死。端到端夹具仍在，但它证明的是**提交结果**而非选块规则——它上面的边界落在旧跨度终点而非内部，两种选择会被 `Math.max(candidatePhysical, mapped)` 折成同一个值。两层互补：纯函数锁映射规则，端到端锁读者历史里最终拿到什么。
3. **1049 双缓冲：缩高与变高已校准，生产实现有三处已复现缺陷（未修）。** 模型按 xterm.js 一手实现重建并自带断言（进出清空/恢复、变矮时 normal 进自己的历史而 alt 丢行、隐藏缓冲区同样被 resize、overlay 的行不进入 normal 历史）。模型先有三处错误——只搬活动缓冲区、拉回时顺序颠倒、变矮误入变高分支导致 `take` 为负——修正后模型在缩高与变高上与发布实现一致，**随即稳定复现三处真实缺陷**：overlay 期间发生的 resize 同时搬动了**隐藏的**主屏，终端已把它推入 normal 的历史；而 alt 分支把待处理的 resize 清掉了，返回帧因此不知道主屏滚过，从冻结边界重画——那个位置已在历史中，于是**同一批行被再次提交**。修复方向明确（返回帧必须采信「主屏已随终端移动」，alt 不得吞掉主屏的 resize），本轮未落实现：三次尝试都只改到一半就与既有断言冲突，与其继续猜，不如把复现留成红的测试。两条用例以 `KNOWN DEFECT` 注释留在 `main-screen-renderer.spec.ts`，并在前置断言里锁住「normal 历史 = line-0..21、主屏 = line-22..29」，使重复只可能来自渲染器。：1049 保存光标、切到并**清空** alt，退出切回 normal 并恢复光标，**不是**两个缓冲区内容互相覆盖；`BufferSet.resize` 同时 resize 两个缓冲区；normal 有独立历史、alt 没有 scrollback，隐藏时 normal 仍调整自己的屏幕与历史。夹具有两条独立断言组：**模型本身**（进出清空/恢复、只有 normal 有历史、隐藏缓冲区同样被 resize、overlay 的行不进入主屏）与**渲染器行为**（既有 overlay 往返、resize-after-overlay 用例在正确模型下全绿）。

过程中先出现的两个"失败"是**模型错了而不是实现错了**：alt 期间的写入仍落在 normal 屏幕上，于是 overlay 一绘制就把主屏的行推进了它的历史，看起来像渲染器重放。修正模型（写入与换行都走当前活动缓冲区）后 93 条全绿。按此结论，alt 分支清 `#resize` 暂未观察到实际违约；这不等于已证明它安全，而是现有输入下没有暴露问题。

这里还分两件事，都不能在 alt 分支里混掉：上次主屏**实际绘制的快照及其文档来源**（在 alt 期间仍是真实的历史事实，用来识别隐藏主屏被终端自然搬走的行），与 resize 后主屏**当前的物理布局和差分 baseline**（已经变了，需要主屏自己的待处理几何）。所以 alt 重绘**不得**用 alt 的 `target` 去更新主屏的快照与来源，也不得只截短或平移旧记录后仍当作"上次绘制的原始快照"——那会丢掉被推走的行；alt 只消费 alt 自己的 resize，回到主屏时先处理旧快照与自然搬行，再由真实的主屏 paint 写入新快照。

当前 alt 分支结尾那行 `this.#resize = undefined` 正是把两种消费混在一起的地方：它把主屏的 resize 也一并吞掉。这是下一项要由行为测试判定的**具体风险**，不能从"来源仍然保留"推导其正确。我没有预先加状态位——试过一个只写不读的字段，删掉了；这一项的形状应由双缓冲行为测试约束出来，而不是现在猜。
4. 复读校正：TypeScript 允许 `interface` 声明 `readonly end`，`exactOptionalPropertyTypes` 并不禁止派生字段；那次报错来自赋值与可选类型。按需读取的最终选择仍然正确，但理由不是「接口不能有派生字段」。

仍有一处不在本轮范围：这个接口只解决「物理屏 → 旧文档」；若宽度或折叠改变了行空间，还需把旧行空间映射到新文档，不能靠它代替既有的 reflow 路径。

### 搜索派生的思考展开：形状通知（已实施）

上一条缺陷的**表现**在搜索这条路上：搜索命中被 run 收走的思考时，那段思考会整段展开（否则命中的文本根本不在屏上），行数因此改变，但 `foldShape` 读的是**宿主集合**而不是**有效集合**，于是形状没变、provider 不会通知 reflow，冻结边界从此与文档脱节。

修法很小：生成 thought mark 时改读有效展开集合。mark key 沿用既有的 `thought:${reasoningKey}`——思考有效展开时该键存在、收起时不存在，宿主展开与搜索派生展开共用同一键，不把 query 或展开原因编码进去；正文始终画出、没有独立开合，不需要新的 answer mark。

两条测试：一条纯渲染确认 mark 的增删、思考真实行起点、以及宿主传入的 `ReadonlySet` 不被改动（含「同一个词同时命中思考与正文」——`thoughtHit` 排除了正文命中，不能拿它代替有效集合）；一条走 LocalTui → renderView → foldShape 比较 → renderer → 滚动假终端的行为链，断言命中的思考在屏上、既有历史前缀不变、随后关掉搜索并继续写入时冻结行不重放。反向变异（退回只读宿主集合）→ 纯渲染测试红。

锚点问题**不留给来源区间工作**：那解决的是物理屏到旧文档，而这里是同一个 answer 在两种搜索目标下导航偏移改变、被 `#reshapedBoundary` 当成几何身份，两者独立。当前 `blockStarts` 在思考起点与正文起点之间切换；已有的实现让命中思考时偏移指向思考行、其余情况指向正文，反向变异测试已锁定这一行为。若后续行为测试显示它不够，正确的方向是**分清搜索定位偏移与稳定绘制锚点**，而不是为思考再扩一类 mark。

### mark 的行必须是思考的绘制行

上一段写的「已有实现」当时并不完整。`offsets[answer]` 被正文起点覆盖，而只有 `thoughtHit`（排除正文同时命中的那种）才把它恢复，于是**宿主主动展开思考、或一个词同时命中思考与正文**时，thought mark 的 `row` 指向的是正文行。provider 的 `firstReshapedRow` 读这个 row，通知起点因此报晚。

修法：保存思考**绘制时的行**并与导航偏移分开——`drawnThoughts` 记录 run 画那段思考时它在正文坐标里的位置，mark 的 row 用它；`offsets` 仍按搜索目标指向思考或正文，供导航使用。这不是新增 mark 类，而是不要让导航偏移覆盖绘制身份。

纯渲染测试相应补强，三处盲区都已修正：原来用 `'line 3'` 做「同时命中」其实根本没匹配到思考（思考是 `lockfile shared`），改为真正共同出现的词；原来只断言文本先后、没有检查 `foldMarks.row`，改为对照 `∴ Thought` 标签所在行（foldMarks 与 blockStarts 同为正文坐标，`bodyRow` 才是帧内偏移）；原来传 `openedGroups` 而没传 `expandedReasoning`，无法证明宿主集合未被改动，改为宿主同时持有 run key 与一个自己展开的思考 key，断言渲染后两者原样。row 修复的反向变异 → 该测试红。

### 行为夹具的局限（如实记录）

走 LocalTui → renderView → foldShape 比较 → renderer → 滚动假终端的行为测试要成立，需要两件事，缺一都会被别的因素掩盖。

**run 必须全程打开，且只有思考的展开与否在变。** 早期版本用 `Ctrl+O` 开 run，那会把成员思考全加进宿主集合，搜索前思考就已展开；改用查询开 run 之后，又曾把查询删空再输入另一串，空查询让 run 关闭、下一串让它重新打开，**run 自己的 open/fold 就足以触发 reflow**，缺失的 thought mark 被完全掩盖。现在的做法是让思考与答案共用前缀 `anchor`：先用 `anchor body 0` 打开 run 而思考仍折叠，确认答案尾部在屏；换查询时**只删掉尾部词、保留 `anchor`**，再补 ` thought 9`。全程命中同一块，run 不会关再开，唯一改变形状的就是思考展开。

**冻结前提要用历史事实锁定，而不是靠文档长度推断。** 断言在搜索之前 `anchor body 0` 已在历史里、`anchor thought 9` 不在，两条都是查出来的结果。

现在两条反向变异都让这条行为测试变红：去掉 thought mark（退回只读宿主集合）→ 历史从 49 行涨到 116 行，即**重放**；让 mark 的 row 跟随导航偏移而不是绘制行 → 同时打红纯渲染与行为链。宿主主动展开思考（不带搜索）的绘制锚点另有一条独立断言，不再只靠双命中那条。

另有两处此前说得不准，一并更正：我曾把「答案行没进历史」归因为「run 折叠时正文只占一行」——**错**，折叠的是过程组，回答无论 run 开合都单独绘制成多行；以及「过度冻结会重复提交」方向写反了，过度冻结是**漏提交**。

### mapper 漏尾：已复现并修复

复核指出一条具体的过度冻结路径：思考独占命中时 `blockStarts[answer]` 被改成思考起点，而 mapper 把同一个 offset 当作绘制跨度的起点。原答案跨度 `[A,E)`、边界 `P` 落在答案内部时，思考展开后答案实际移到 `A+Δ`，但跨度起点变成更早的 `T`，旧跨度与新跨度长度不等，mapper 于是返回新段尾 `E+Δ` 而不是应保留的 `P+Δ`——把原先未冻结的答案尾一起冻结。二者相差 `E-P`，正好是那段未冻结的尾巴。

复核先纠正了夹具结论，这一处更正**分两版、不要混记**：最早那版逐字符输入会经过**空查询**中间帧，run 因此关闭再打开，run 自己的 open/fold 触发 reflow，把缺失的 thought mark 掩盖掉；改成**共同 `anchor` 前缀**之后问题变了——退到 anchor 时是**双命中**，思考先展开而导航起点仍在正文，mapper 先按正确的正文锚点消费了通知；随后切到思考独占命中时导航起点才移动，而 `foldShape` 不再变化，所以那一版**仍然分不出** `blockDrawStarts`。真正避开中间帧的是**整串写入 + Enter 确认**。两版都记在这里，是因为它们掩盖的是不同的东西。缺陷随后复现：冻结停在 `anchor body 32`，`anchor body 33` 从未进入历史，而它之后每一行都进入了——是已提交前缀里的一个洞。

复核随后又指出**我第一版修法自身是错的**，两点都成立：写 `blockDrawStarts[answer]` 时我自己按 `thoughtHit` 把它指向了思考（方向反了）；run 成员的收尾循环又用 `offsets` 全体覆盖了一遍，而 `offsets` 早已被搜索改成思考行——于是 `blockDrawStarts` 最终等于 `blockStarts`，先前保存的值被冲掉。所以「改了前后一样、根因不在这里」这个结论**当时并不成立**，我是在一个没真正生效的改动上得出了否证结论。

现在两侧都真正分开了：答案的绘制起点恒为其正文首行，**不看 `thoughtHit`**；成员收尾循环只在尚未写入时才填，不再覆盖；mapper 读 `blockDrawStarts`（缺省回退 `blockStarts`）。夹具还有一处独立错误也一并修掉：输入完整查询后状态是 `editing`，回程直接写下一段会被**追加**成 `anchor thought 9anchor body 0`，不再匹配、run 折叠；现在回程先 Enter 确认再写。

两条反向变异都让行为测试变红——成员循环改回用 `offsets` 覆盖、以及 mapper 改回读导航 offset——另加一条纯渲染断言锁住「思考独占命中时导航 offset 与绘制起点不同、无搜索时两者相同」。正向断言取**冻结边界之外的第一条答案行**，下标从历史读出，并先断言历史里的答案编号是**连续前缀**（否则 `max(N)+1` 只说明最大编号之后没有记录，掩盖了中间可能已有的洞）。

### 从 Codex 借鉴：保留「scrollback 不可改写」，改位置模型而非历史模型

读完 `codex-rs/tui` 后与 Codex 对过一轮，结论如下（这一节记录的是**取舍与顺序**，不是已实施的功能）。

**不借鉴它的核心模型。** Codex 把终端 scrollback 当可重建的投影：`app/resize_reflow.rs:3-5` 描述的是「用存储的 cell 当源、清掉 Codex 自有的历史、按新终端尺寸重发转录」。本项目的契约是相反的——`AGENTS.md` 写明进了原生 scrollback 的行是不可改写快照，「不得用重放或清空来'修复'它」。这不是写死的包袱而是产品取舍：历史保留读者当时看见的，当前视口展示最新投影，两者本就该有分歧。因此**保留契约，不改历史语义**。

**要借鉴的是位置模型。** Codex 的滚动锚点不是行号，而是 `(单元格身份, 单元格内偏移, 行偏置)`（`transcript_view.rs:61-68`），展开态按**稳定名字空间身份**保存（`history_cell/mod.rs:247-251`），搜索进入时保存位置与展开态、退出时恢复（`transcript_view/search.rs:88-104`）。这些都不要求放弃 scrollback 契约——位置模型和历史语义是两件独立的事。本项目用行号当冻结边界，导致搜索展开思考后必须发 reflow 通知才能不让边界漂移；换成源锚点可以从根上减少这一类通知（但**不取消**通知：布局真的变了仍要让 renderer 解析新位置，减少的是相邻跨度猜测，不是布局变化本身）。

**顺序（复核建议后调整）**：主屏/alt 的 resize 生命周期与记账 → 稳定身份与带来源的布局投影 → 基于锚点的搜索保存/恢复。窄屏宽度助手（`width.ts:23-48` 的 `usable_content_width` 返回 `Option`，而非可能为零的宽度）是成本极低的独立改进，可提前做。

**明确不借鉴**：清历史重放（与契约冲突）；`EntryKey::Cell(Arc 指针)` 这种身份——本项目的 block 会因流式更新被替换，对象身份不稳定，需要**文档 epoch + 稳定块 id + 内容分段（body/thought）+ 源文本内偏移**；Codex 的 owned-screen 折叠政策（本项目默认就是 run 折叠，不因它撤掉）；它的整条视图状态机。

**一处必须写清楚的限制。** Codex 的可重建模型不需要知道终端搬了几行，因为历史会重发；本项目保留快照，就**必须**知道。复核指出：普通 TTY 下无法读出隐藏 normal 缓冲的实际历史，`#committedByTerminal` 也仍在用 `oldHeight - height` 这种万能公式。在明确的终端行为模型下（xterm.js `Buffer.resize`：同宽缩高时先移除光标下方行，剩余收缩才推入历史，推入数为 `max(0, oldCursorRow + 1 - newHeight)` 而非 `oldHeight - newHeight`）可以推导，但这**不是跨终端保证**。同样地，`provider-local.ts:604` 在 multiplexer 分支要等 debounce 到期才采样尺寸，中间尺寸已经丢失——几何记账应尽量在 resize 回调里立即进行，debounce 的只是格式化与重画。

因此下一步**不是**先造一套通用的 pending 状态机，而是：先把「同宽缩高 + normal 光标已知 + alt 重画后返回」这一条已复现路径，在一手实现与真实支持终端上校准模型，再用它修；宽度变化、变高与未观测的突发各自作为独立输入验证。**未知搬行不得偷偷按零处理然后宣称「不漏不重」**——那正是本项目已经犯过一次的假绿。

#### 假终端已按一手实现校准，修复尚未落地

对照 xterm.js `Buffer.resize` 的实际实现（本项目的 `Emulator` 之前按高度差推顶部行，**是错的**）校准了模型：变矮时逐行判断，**光标下方**有空行就删掉它、只有没有空行可删时顶部才进入历史（`max(0, oldCursorRow + 1 - newHeight)`，非 `oldHeight - newHeight`）；变高时**光标在底部**才从历史拉回、光标随之��移，光标不在底部则只补空行。两条模型断言把这条规则钉住：光标在第 7 行时从 10 缩到 8 **不入历史任何行**，光标在最后一行时才入两行——只测后者的话，按高度差写的实现同样会绿。

**归因更正。** 本文档此前同时留着两句互相矛盾的话：一句写「模型已闭合，三条失败都归 renderer」，另一句写「4 条既有测试变红，说明它们编码了旧模型」。两句都不成立——第一句范围过大（**宽度变化至今未建模**），第二句把锅推给了测试，而复核正确地指出变红的是**当时保留的实现**：它同时检查错两处（`resize` 开头已改 `height` 却拿它比底行；拉回内容却让光标原地不动）。按独立发布实现定案后那 4 条全部转绿，测试本身没有问题。

当前准确状态：缩高与变高的**数量与光标行为**已对照源码并经 `@xterm/headless` 6.0.0 交叉校准；**宽度未覆盖**；三条 renderer 缺陷在已校准范围内归 renderer。`#committedByTerminal` 仍用 `oldHeight - height` 这个已知错误的公式，这是修复的起点。

`#resizedScreen` 变高时的几何假设存在**一处真实缺陷，已修**。供 diff 使用的 baseline 必须描述**本次输出前的物理屏幕**，而不是渲染器自认画过的屏幕；未知处宁可给一个匹配不上的行，让它被重画。真实终端变高把新行加在**底部**，旧行原地不动；`#target(..., 'bottom')` 则把 5 行文档锚到 7 行窗口的下方，即 `['','','a'..'e']`。旧实现在顶部前置空白，得到的 baseline **恰好等于 target**，于是逐行 diff 认为无需重画、只发出一个裸 CUP：文档停在 target 已经挪走的位置上，而 `#finishPaint` 仍把 `target.rows` 记为已画出的屏幕，渲染器的屏幕记忆从此与真实屏幕不一致。

这里我犯过一个方向相反的错误，值得记下：先看到 headless 忠实执行了错误输出，就断言「原实现正确」，理由是「真实终态是底部空白」。**终端忠实执行错误输出，并不能证明输出符合目标布局**——两者只在渲染器随后*记住*什么上才分岔。区分办法是把两件事分开问：baseline 回答「终端现在屏幕上是什么」（是底部空白），target 回答「这一帧要画出什么」（是顶部空白）。我那条「顶部空白断言只看了中间态」的说法同样与 trace 不符——trace 里的中间态正是底部空白。已撤回该结论与那条错误断言，改为保留经校准的 target 终态作为回归。

**我随后又写错了一次范围。** 我当时说「只修了无历史那种 grow、其余拉回输入未动」——落盘代码并非如此：改动是**无条件**的，所有 grow 一起变了。复核给出的最小反例（有历史被拉回 + 同帧追加两行）按我的写法得到 `[p0,p1,a,d,e]` 而非 target `[a,b,c,d,e]`：`p0,p1` 留在屏上、`a,b,c` 根本没被重画，屏幕记忆再次记成未画出的 target。已用 headless 校准该反例：3 行 `[a,b,c]` + 历史 `[p0,p1]` 变高到 5 行，真实屏幕是 `[p0,p1,a,b,c]`。

两次尝试（统一前置、统一追加）都错，根因是**本渲染器不持有终端 scrollback 的模型**，因此既无法判断发生的是哪一种 grow，也无法知道被拉回的行是什么。而普通空串不是「未知」的可靠表示——它会与 target 空白精确匹配，正是需要重画的行被跳过的原因。所以最终不再伪造位置：**任何高度变化**都把 baseline 标为**不可知**、直接重画整个视口；等高才沿用原 baseline。（此处曾写「缩高只删底行、幸存行可知、保留原 baseline」，与落盘不符，已删；缩高同样有把行推入历史的形状，见下。）

代价是一条既有测试放宽了断言：它原先禁止变高帧出现 `2J`。本渲染器从不发 `3J`，而 `3J` 才是**永久抹掉原生 scrollback** 的那个序列；`2J` 只清可见屏幕。该测试真正的契约——原始 tape 在变高后仍以同序存在——原样保留并仍然通过。断言已收窄为只禁 `3J`，并写明理由。

两条 grow 测试的变异覆盖已实测：追加式 baseline 两条都红；前置式 baseline 在**无历史**那条红、在**拉回**那条绿（前置恰好也改了第 0-1 行、从而碰巧触发了重画——在这条上「因祸得福」，但正是无历史那条测试排除了它）。两条互不替代，这一点已写进测试注释。

**缩高原先也被我描述错了。** 我写「缩高只删底部行、幸存行可知」，但落盘代码是 `this.#screen.slice(oldHeight - this.#height)`，删的是**顶部**、保留的是末尾那几行。复核给出的反例（H5、文档 7 行、`liveStart=2`、光标置于 a）实测为 `[c,d,e]` 而非 `[a,b,c]`：光标不在底部时终端从底部删行、真实屏幕是 `[a,b,c]`、历史不变，而该 baseline 描述的是 `[c,d,e]`，与 target 完全相同，于是漏掉重画。既然变高已经如此，缩高一并改为「baseline 不可知 + 重画视口」。

**记账是另一笔账，与 baseline 分开。** 同一条输入里 `candidatePhysical = physical = 2`，而 resize 分支的最后一个 else 直接设 `physical = viewStart = 4`，把**尚未进入历史的** a、b 误记为已提交并冻结。headless 校准确认 a、b 从未进过历史。但这里不能简单改成停在 candidate：光标**在底部**时终端确实会把行推入历史（5 行 `[p1..p5]` 缩到 2 行，真实历史变为 `[a,b,p1,p2,p3]`、屏幕 `[p4,p5]`），此时停在 candidate 会把终端已经搬走的行再冲一次，造成历史重复。两种真实形状的判据是**resize 之前光标停在哪**——与终端自己用的信号相同，而 `#cursorRow` 在该分支里仍持有 resize 前的位置（会移动它的那一帧尚未绘制）。实测两个单边变体都被抓：一律 `viewStart` 红 3 条、一律 `candidatePhysical` 红 4 条，所以这个分支确实需要区分，而不是任选其一。

同一轮还暴露一个夹具问题：三条失败用例构造 renderer 时都没给 `width`（默认 0），随后 `resize(80, …)` 会同时置 `widthChanged=true`，把宽度路径混进了「纯高度」的证明里。三处已显式给 `width: 80`，高度变化才是被验证的那件事。`↑` 用例的注释也已更正：9 行浏览帧下光标被钳到物理第 8 行、第 9 行是填充，所以 10→8 只删底部填充并把**标记**推入历史，不是「标记和下面第一条正文都推走」。这条更正当时只落到中段注释，JSDoc、用例名「commits the document row a shrink **pushed** below an overflow marker」和后半段仍在说「终端把下面那行也推走了」，现已一并更正：用例名改为 `…a shrink **did not push**…`，JSDoc 写明这是**主屏浏览**缺陷而非 alt，并说明 `line-12` 应当由 renderer 主动补交、不能当自然提交来抵扣。

该用例现在在**返回 paint 之前**先读终端自身状态并钉住事实：历史里有溢出标记、**没有** `line-12`。这是唯一能分辨两种行为的时机——一旦那一帧画完，renderer 提交了或跳过了 `line-12` 都与「终端做的」无法区分；只做事后断言就分辨不了。`line-12` 与 `line-8` 各一次的到达断言保留在之后。

另有一处独立的信息丢失待修：`provider-local.ts:604` 的 multiplexer 分支等 debounce 到期才采样尺寸，中间尺寸已经丢失，而上述推导逐步依赖每一轮的几何。几何记账应前移到 resize 回调，debounce 的只是格式化与重画。

## 相对 v1 的修订

v1 是只看 oh-my-pi 得出的结论。读过官方实现后，有两处必须推翻：

| | v1 结论 | 官方实际做法 | 判定 |
| --- | --- | --- | --- |
| 工具失败时 | **强制展开**输出框 | 错误文本**提进折叠摘要行**，不强制展开 | v1 错。摘要行直接显示失败原因，展开与否交给用户，信息不丢而噪声更低 |
| 折叠粒度 | 每个 tool 一行 | 一个 turn 内的过程归为一个 **process group**，组头是**类别聚合** | v1 太浅。官方是两级折叠，v1 只想到一级 |

另有三处 v1 遗漏或写错：

- v1 的 UI 稿给折叠行画了 `⏱ 12.4s` 耗时。官方折叠行**不显示耗时**，后缀是 diff 增减 `+N -M` 或视图自定义后缀。
- v1 沿用 `TOOL_COLLAPSED_LINES = 10` 的"偷看 N 行"语义。官方**没有任何行数上限**——工具输出要么全显、要么全隐。这两种语义不能混用，见 D7。
- v1 没意识到折叠密度应该是一个**用户设置**而不是一次重设计。官方用一张四行策略表解决（见 D3）。

## 官方折叠基线

以下均来自 `refs/deepseek-harness`，是 omdsh 的参考而非依赖。

### 两级折叠

**外层 · turn process window**：一个 turn 关闭后整块折叠，折叠条件是 `foldCompletedTurns && turnClosed && !alwaysOpen`（`packages/client/ui-chat/src/client/chat/ChatGroupSeat.tsx:152-153`）。

**内层 · step/process group**：turn 内的 reasoning、tool call 归为一个组，用 `useDisclosure()` 控制（`ChatGroupSeat.tsx:136`）。

两层状态都是**内存态**，不随 reload 或 resume 保留；持久化的只有密度模式本身（`chat-settings.ts:1-12`）。

### 策略表

`packages/client/ui-chat/src/client/presentation-policy.ts:24-53`：

| mode | `foldCompletedTurns` | `stepGrouping` | `liveProcessDetail` | `settledReasoningPreview` |
| --- | --- | --- | --- | --- |
| `compact` | true | `collapsed` | false | false |
| `standard` | true | `collapsed` | true | true |
| `detailed`（默认） | true | `history` | true | true |
| `verbose` | false | `none` | false | true |

渲染器**只读布尔字段，不比较枚举**（`presentation-policy.ts:1-4`, `:74-77`），加一个模式是改一张表的事。

### 分组是一等模型

`GroupSnapshot<Data> = { key, data, members: readonly NodeReference[] }`（`packages/client/ui-conversation/src/client/contract/groups.ts:29-33`），存在 `ConversationGroupStore` 的 `Map` 里，配一个 `NodeKey → Set<groupPart>` 的位置索引（`conversation/group-store.ts:44-48`）。

`NodeReference` 可以只指向一个 Node 的**某一部分**（`groups.ts:13-17`），所以同一个 assistant 记录的 reasoning 可以进组、回答留在组外。

打断规则五条（`conversation-nodes/process-groups.ts:146-165`）：顺序断裂、遇到独立节点（user / steering / turn-trigger / model-retry / turn-error / turn-max-tokens / turn-tail）、assistant 产生回复内容、`turn-process` 独立成组、turn 结束关闭全部。

组键由内容派生 `brandString(['process', first.key, first.groupPart])`（`:132`），`extendedGroup`（`:173-190`）只在整组连续存在时复用旧键，使披露状态在流式追加中不丢。

### 组头是类别聚合

`ProcessActivitySummary.counts[]` 是按类别排序的计数（`contract/process-groups.ts:6-12`），类别含 read / write / edit / search / commands / subagents / plan / questions（`ChatGroupSeat.tsx:37-52`）。

关闭态标题由 `processTitle()` 生成（`step-process.ts:11-28`）：取**前三个类别**，**不带次数**，两个类别走 `joinTwo` 模板并做 `sharedPrefix` 去重，超过三个时追加 `and N more`。

运行中标题另有 `liveProcessDetail` 控制，并带 **150ms 防抖**（`PROCESS_TITLE_MINIMUM_MS`，`ChatGroupSeat.tsx:27`, `:58-81`）——这是行为防抖，不是动画，目的是让一串快速工具调用不把标题闪成一团乱码。

### 错误进摘要行

这是推翻 v1 的那条。`ToolRow.tsx:182-183`：

```
failureLine = state === 'error' ? errorSummary ?? normalSummary : null
```

失败时**摘要行本身**换成错误首行。`useDisclosure` 无条件初始为关闭（`use-disclosure.ts:11-21`），`ToolRow.tsx:171` 的 `open = expanded && expandable` 从不覆盖它。

唯一的强制展开在 **turn** 级，且看的是 turn 的结束原因而非单次工具失败：`turnProcessAlwaysOpen` 对 `status === 'open' || reason === 'aborted' || reason === 'error'` 返回 true（`contract/turn-process.ts`，消费于 `ChatGroupSeat.tsx:146-147`）。

### 思考预览

reasoning 是 assistant 消息里的**独立有序 block**（`AssistantBlock` 五路联合 `text | reasoning | image | tool-call | other`，`records.ts:33-38`），不是扁平字段。

折叠态摘要算法（`ReasoningRow.tsx:11-32`）：

- **流式中**：取**最后一个完整段落**的首行（按空行切段），因此永远不会显示半句。
- **已结束**：取全文首行。
- 剥离 `**` 标记，**不显示 token 数、不显示耗时**。

展开后是完整 Markdown（compact 变体，`ReasoningRow.tsx:69-72`）。

### 通用回退行

没有专用视图的工具走 `GenericToolCard`（`packages/client/ui-tool/src/client/tool/toolviews/GenericToolCard.tsx:33-74`），摘要由纯函数 `deriveSummary`（`models/tool-call-model.ts:226-240`）派生：

- 先 `JSON.parse` 失败则当原始字符串（流式截断的 args 也走这里）。
- 按工具族取第一个非空字符串键：`bash: description|command`、`read: path|file_path|url`、`search: query|pattern|url`、`write/edit: path|file_path`、`code: description`（`:215-223`）。
- 再退到任意首个字符串值属性，再退到原始 args。
- 一律 `firstLine` 截断。
- 路径相对 `cwd`、home 缩写为 `~`（`:293`）。
- 折叠行**无行数上限**，靠 CSS ellipsis 处理宽度（`ToolRow.tsx:41-47`）；`summarySuffix` 刻意放在 ellipsis 之外，让窄屏先裁摘要、保留尾部事实。

注册机制是单一 keyed slot `tool.call.toolview`，`renderSlot(..., { fallback: <GenericToolCard/> })` 一次原子派发同时覆盖根调用和递归子调用（`ToolCallTree.tsx:57-61`, `:90-108`）。

### 按工具的行数上限

只对**展开后的正文**生效：read 与 search 各 8 行（`ToolRow.tsx:269`, `:293-298`），diff 走 `CHAT_DIFF_MAX_LINES`，**bash 是 `Infinity`（可滚动）**（`bash-sample.tsx`、`ToolRow.tsx:259-264`）。折叠行本身没有上限。

## 可借鉴 vs 不可借鉴

**结构性（可移植）**

1. reasoning 作为独立有序 block，而非扁平字符串字段。
2. 四行策略表 + 渲染器只读布尔。
3. 组作为一等不可变快照 + 稳定内容键 + 独立位置索引。
4. `NodeReference` 可指向 node 的某一部分。
5. 组键内容派生 + 连续性复用键。
6. 五条打断规则。
7. `counts[]` 聚合模型与"前三类别 + and N more"的关闭态标题。
8. 150ms 运行标题防抖。
9. 错误提进摘要行。
10. `deriveSummary` 的按族取键 + 首行截断 + 路径相对化。
11. 单一 keyed registry + 强制通用回退。
12. 折叠时不构造内容（`ReasoningRow.tsx:70-74`、bash 视图同构）。

**web 专属（不要移植）**

1. `hidden="until-found"` + `beforematch` 浏览器查找揭示（`searchable-hidden.ts:21-29`）。终端没有"已布局但隐藏"这个状态——可见性就是**不发出单元格**。
2. `max-height: min(400px, 50vh)` 的组体上限与淡出边（`ChatGroupSeat.module.css:76-77`）。终端没有 `50vh`，回滚区里再嵌一个滚动区是糟糕交互。
3. `use-process-scroll` 整套机制（`ResizeObserver` / `scrollend` / 平滑滚动 / 边缘淡出）。
4. 全部 DOM / ARIA / 动画 / React 机制。
5. `openFile` 拉起宿主编辑器、`loadImage` 图库 slot。
6. CSS ellipsis 处理宽度。**这是最需要改写的一处**：终端必须按显示格预算截断（`AGENTS.md` 已有规则），纯模型要接受"可用宽度"参数而不是吐出整串。
7. `presentCall` / `presentResult`：**全仓零消费者**。它们只是声明式词汇（`packages/core/tools/src/index.ts:290`, `:298`），软校验失败返回 `undefined` 以便回放旧日志（`schema.ts:609-624`），但 `apps/web`、`apps/desktop`、`apps/cli`、`packages/client`、`packages/tui` 里没有任何渲染器调用。**不投入。**

## omdsh 改造方案

### 决策

**E1 · 采纳两级折叠。** 外层 turn process window + 内层 step group。当前 omdsh 只有"每个 tool 一个块"这一级。

**E2 · 错误进摘要行，不强制展开**（推翻 v1 的 D1，批次二已实施）。工具失败时折叠行直接显示错误首行，并按 error 颜色上色；展开才看完整输出。信息不丢，噪声更低，且与官方一致。turn 级的整组强制展开等批次四。

**E3 · 引入策略表。** `compact | standard | detailed | verbose` → 四个布尔，渲染器只读布尔。折叠密度进 `/settings`，不再是一次性重设计——这同时回答了"这个框到底该不该存在"，答案交给用户偏好。

**E4 · 思考预览取最后一个完整段落的首行**，流式时不显示半句。需要把 `reasoning: string` 从扁平字段提升为独立 block（对齐官方 `AssistantBlock` 联合）。

**E5 · 采纳 `deriveSummary` 的按族取键规则**，并把 CSS ellipsis 换成显示格预算。折叠行不加耗时，尾部放 diff 增减 `+N -M`。

**E6 · 折叠时不构造内容。** 终端直接不产出行，不做"渲染后遮盖"。

**E7 · 不做"偷看 N 行"。**（批次二已落地，见 P4）官方对折叠行没有任何行数上限，只有全显或全隐。原来的 `TOOL_COLLAPSED_LINES = 10` 预览路径在折叠后不可达，已整段删除，现在只有一行和全文两种形态。

**E8 · 运行中组标题 150ms 防抖**，避免快速工具调用把标题闪成乱码。

**E9 · 折叠态持久化——与官方有意分歧。** 官方只持久化密度模式，逐条披露状态丢失。我们有 `--resume`，会话从磁盘恢复，用户大概率希望折叠态跟着回来。建议与 E3 的密度一起持久化到 profile。

**E10 · 不实现 `presentCall` / `presentResult`。** 零消费者，投入无回报。

**E11 · 折叠行光标仍然需要**（保留 v1 的 D2 结论）。官方用点击展开，终端没有鼠标。这条与官方无法对齐，只能自建。

## 批次五：策略表（已实施）

`session/fold-policy.ts` 独占这张表，`/settings` 只暴露名字，provider 解析成布尔，渲染器只读布尔。四个档位落在三个折叠面加两个从句开关上：

| 档位 | groups | tools | reasoning | detail | subject |
| --- | --- | --- | --- | --- | --- |
| compact | ✓ | ✓ | ✓ | ✗ | ✗ |
| standard | ✓ | ✓ | ✓ | ✓ | ✓ |
| detailed | ✗ | ✓ | ✗ | ✓ | ✓ |
| verbose | ✗ | ✗ | ✓ | ✓ | ✓ |

三条设计约束，都是被测试逼出来的，不是先想好的：

1. **不能有一个档位把三个面全展开。** 那样 `Ctrl+O` 在该档位下无事可做，按下去没有反应会被当成坏键而不是满屏内容。所以 `verbose` 保留思考折叠。
2. **工作（groups / tools）沿档位单调递增，思考是唯一的例外。** `detailed` 展开思考，`verbose` 又把它折回去。这不是疏忽：`verbose` 要的是「完整的工作」，不是「模型的心声」，而且这一档的说明文字在用户选之前就写明了。测试直接锁住这个非单调点，改表就会红。
3. **两个最安静的档位必须在最常见的场景里就有区别。** 最初只用 `subject` 区分它们，结果一整轮工作（无失败、未搜索、未 focus）默认就是折叠的，两个档位**逐字节相同**——一个只在罕见路径上生效的开关等于没有开关。加上 `detail`（组头是否写出工作种类）之后，折叠状态下那一行就分出长短。

**与旧设置的迁移**：`expandTools` 保留在 schema 里只读不写，`resolveFoldDensity` 把它映射到 `verbose`。`prefs()` 不再回写该字段，所以 profile 第一次保存后自动完成迁移。理由与 `statusPreset` 完全一致。

**E9 逐条折叠态持久化：有意不做。** 原计划认为「有 `--resume`，用户希望折叠态跟着回来」。实施时发现三条理由压过了它：

- **它和密度抢同一个问题的答案。** 密度说「这些应该折起来」，逐条状态说「那一条我打开过」。两个真相来源打架时，读者看到的行为无法预测。
- **无界增长且永不回收。** 键是 `tool:<callId>`，一次长会话里每个按过的调用都留一条，没有过期、没有上限，会话被弃掉也不清理。
- **它是瞬时检视动作，不是偏好。** 密度是对「静置形态」的陈述，逐条打开是「我现在要看这一条」。把后者写进磁盘，等于把工作台上的临时摊开状态当成明天还要继续的现场。

代价是诚实的：`--resume` 之后要重新按一次 `Ctrl+O`。这条已经写进 CHANGELOG，不是留给用户去发现。

| 思考折叠忽略密度 | 1 |

**实施陷阱（新增两条）**：

1. **缓存键测试必须复用同一个 `TranscriptState`。** 最初写成两次 `view()` 各建一份 state，块数组身份不同 → 缓存必然未命中 → 删掉 `foldKey` 比较测试照样绿。要锁住缓存键，两次渲染必须喂同一份 state。
2. **终端断言要读屏幕，不要读输出增量。** 未变化的行不会被重绘，所以「折叠了」这件事在增量里根本看不见（没变＝没输出），而屏幕上那个框还明明白白摆着。必须用 `emulatedScreenRows(term.captured)` 读回最终屏幕，并且以**边框**为标记：折叠行是 `✔  bash`，展开是 `╭─── ✔ bash ───`；输出文本不能当标记，因为折叠行自己的 fact 就可能是输出的第一行。

## PTC 子调用（已修复）

PTC（programmatic tool calling）模式下模型不再直接发 `tool/call`，而是发一个 `run_code`，程序里的每个工具调用记录为 `tool/ptc-dispatch-start` / `tool/ptc-dispatch`（`packages/core/tools/src/types.ts:9-25`），携带 `rootCallId` / `parentCallId` / `subCallId`。这些事件**只进日志，不进模型上下文**。

上游的契约给了一句决定做法的话：子调用应当 "render a sub-call through **the exact path used for a native call**"（`types.ts` 中 `tool/ptc-dispatch` 的文档）。因此**不采用官方 Web 的递归树**，而是让子调用走我们已有的 tool 路径：

- `tool/ptc-dispatch-start` 走与 `tool/call` 相同的 `startToolCall`，块上多一个 `parentCallId`。
- `tool/ptc-dispatch` 走与 `tool/result` 相同的 settle 路径。
- 渲染时缩进两格并压缩宽度预算，读者一眼能看出这不是模型直接要的工具。
- `TuiToolPresentationBridge` 也认这两个事件：dispatch 事件自带 name 与 arguments，不需要 call 索引，所以子调用拿到的卡片和同工具的原生调用完全一样。
- 窗口切断：dispatch 事件自带 name/arguments，settle 没有对应 start 时**自建块**而不是丢弃。官方为此专门处理了这个 case；丢掉就等于在一份确实保存了的记录里留一个洞。

修复前主 transcript 只读 `tool/call`，一条 PTC 回合只显示 1 行，内层调用全部静默丢失（`/trajectory` 检视面一直是对的，它已经处理了这两个事件并用 `parentCallId` 标为 `SUBTOOL`）。14 条新测试中 10 条在旧行为下失败，逐条覆盖了上述每一条。

## resize 校准与修复记录

本轮全部校准用 `@xterm/headless` 6.0.0（`pnpm-lock` 里已有的传递依赖，记录的 commit 与复核读到的一致），方式是把 renderer **真实输出**原样喂进去，每次等解析回调完成再读 `buffer.normal`（不是 active），并记录 `cursorY`/`baseY`/可见行/历史。测量脚本是一次性探针、不进仓库；结论以测试与注释的形式留在 `main-screen-renderer.spec.ts` 里。

**浏览漏交已修。** 复核指出「不需要来源判定」这个说法过宽：已有逐行来源过滤正是修法的一部分，缺的只是**数量**；该输入可先纠正数量，不必新增接口或前缀邻接算法。两处都改了，且都不是换候选行号，而是复用正确的自然推行数量与现有来源/内容核对、保留区间差集。

- **推行数量不是高度差。** 旧光标在第 8 行，10→8 实际只推 1 行——删 1 条 padding、推 1 条标记，共缩 2 行。旧代码按高度差 2 计算，误把 row1 的 `line-12` 算进去。已改为 `max(0, min(光标行+1, 旧高) - 新高)`。
- **非正文行不「跳过」也不「截断」，而是按来源映射逐行取。** 原来的「跳过」在一个方向上错，我第一次改成「一律截断」又在另一个方向上错。headless 三组输入定案：5 行 `['','','a','composer','footer']` 缩到 1，光标在末行 → 历史 `['a','composer']`（两条 padding 先走、**没有**阻止推行）；同一屏光标在第 2 行 → 历史为空（推行在 padding 处结束、没碰到 `a`）；`[marker, line-1..line-4]` 缩到 3、光标在末行 → 历史 `['marker','line-1']`（标记走了、它下面那行也走了）。所以**推了多少行由光标决定、能抵扣哪些正文由逐行来源决定，两者互不推导**。
- 该公式**仅用于缩高**。变高是把历史拉回屏幕内，是另一件关于物理屏幕的事实、此处推不出来，所以变高不抵扣任何区间、只重画；不限定时 6 条既有测试变红。

↑ 用例的 padding 文字也已更正为「删 1 条 padding、推 1 条标记」，此前写成「删两条底部空白」。该输入里 **padding 与标记都不是正文**，所以终端自然提交的正文行数是 **0**——`line-12` 完全是 renderer 该补的。（此前写成「共两行、只有一行是 document row」也不对：标记同样不命名任何 document row。）

**alt 路径的两条校准结论。**

- 10 行主屏 → 进入 1049 → overlay 打开期间 `resize(80, 8)`：真实终端**两个缓冲都搬**，隐藏的 normal 从 `[m-0..]` 变 `[m-2..]`、历史 `[m-0,m-1]`、光标钳到 7。
- 「honours the resize…」那条的断言口径此前是错的：它先把 `doc(30)` 缩成 `doc(2)` 并 reflow，初始历史已含 `head-8`，reflow 后主屏顶部又是 `head-8`、旧光标在底部；随后 10→9 时隐藏 normal 会自然把 `head-8` 再推一次，**返回 paint 之前它就已经有两份**。这是终端拍下当时屏幕的快照、不是 renderer 主动重交，所以对 `head-8` 断言 `<= 1` 会让用例在修好返回逻辑后依然红。已改为：先在返回前读终端状态、记录各标记的**自然提交份数**（`head-8` 两份、`head-9`/`head-10` 各一份），再以**记录到的自然份数**为上界断言返回后没有额外重交，并断言返回前已提交的行仍以同序存在。没有简单放宽成 `<= 2`——那会藏住真正的重交。

**关于变异验证的一条更正。** 显式传参之后，只把「清字段」提前的单点变异仍然有意义：保留正确参数的版本在这个输入上本来就与修好的实现等价，不该被当成变异无效。要复现一个**组合**缺陷才需要整体回退。单点与整体变异各有用途，不能相互取代。

**alt 返回已修（此前三条剩余缺陷现已全部转绿，`main-screen-renderer.spec.ts` 108 条全过）。** 复核给的顺序是：alt 重画只消费自己的状态、保留主屏旧 transition 与旧光标及来源快照；**首个返回主屏的 paint 之前**先核算自然提交区间，再做区间差集与必要的邻接推进，最后画新主屏并更新快照；来源/邻接与修复一起落实。落盘按此实现：

- overlay 分支不再丢弃主屏的 transition，而是连同**主屏自己的光标行与逐行来源快照**一起 park 到 `#mainResize*` 上；overlay 仍然只结算自己的布局。
- park 放在 `render` 里而不是某个 paint 路径里，因为「返回主屏的那一帧」既可能是跟随 transcript（`#paintFollow`），也可能是浏览帧（`#paintTransient`）——最初只放在 transient 路径里，1049 用例的返回帧走 follow，于是 park 根本没发生。
- park 的自然提交区间用的是**移动前的光标行、移动前的来源映射、当前的文档文本**，即与一次可见缩高同一套判定；算出后**当场把 `#physical` 推进到该区间末尾**。原先想把它留作「待扣除区间」，但返回主屏的帧总是整屏重画（`leavingAlt` 强制 clear），不会走到做差集的 flush 分支，留着只会被无关帧消费或直接丢掉。
- park 是**一次性**的：还原完就清掉 `#resize`，否则 overlay 的「每次 resize 只 clear 一次」会被重新武装、之后每帧都 clear。
- overlay 的 clear 判定改为只看**它自己那份** transition，避免主屏的 transition 回来后误触发。

变异验证：去掉「推进 `#physical`」这一句 → 红；把 park 换成一个空操作（等于旧的丢弃行为）→ **不红**——说明 1049 用例目前只能证明「边界推进」这一半，park 本身没有独立守护。这一点如实记下，不当作已覆盖。

**复核指出的三条可由代码推出的失败路径，两条已修、一条部分修完。** 三条都属实。

1. **pending 被下一次 alt 重绘提前消费** —— 已修。restore 现在只在**真正返回主屏**的那一帧运行（`transientSurface !== 'overlay'`），overlay 重绘不再拿 overlay 的 `next` 去核对主屏来源；park 也只在有真实 transition 且当前没有 pending 时写入，因此普通 alt 重绘不会再用 `undefined` 覆盖旧 pending。行为测试：连续两次 overlay 重绘后返回，被终端提交过的行仍各只有一份。变异「restore 不看是否返回」→ 红。

2. **browse 的坐标错位** —— 修了取文本的方式，但**没有**做完。`#committedByTerminal` 现在按 frame 声明的 `documentRows` 把 document 下标换算成 frame 下标（窗口起点 20 的 document row 20 是 `next[0]`），不再用绝对下标；快照比较也不再依赖返回帧，而是用 park 时保存的主屏行与逐行来源。**但一个看不到那些行的窗口只能得到「未知」**，而「未知」既不是「终端什么都没提交」也不是「终端都提交了」——把它当成后者会漏发当成前者会重发。目前的处理是：这种帧不产生 credit、snapshot 保留，交给下一个带文档的帧解析。**这条只做到了「不臆断」，还没做到「browse 返回后最终正确结算」**，browse 场景下的完整解析留作下一步。

变异「用绝对下标」→ **不红**：现有输入里 browse 帧的窗口恰好没落到那个分支，所以这条守卫目前**没有回归守护**。

3. **邻接不是整理而是漏行** —— 已修，这条最要紧。原来 `#physical = max(physical, credit.end)` 会把 8..21 整段标成已提交，8..19 永久丢失。现在自然提交**保持为一个区间**，只有与冻结前缀**邻接**的那部分才推进 `#physical`，不邻接的部分留作待扣除区间，由 flush 做**并集差集**（两个区间分别处理，不合并——合并不相邻的区间会把中间的缺口一起盖掉，那正是还欠着的行）。行为测试：H10、`liveStart` 8、终端自然提交自己那两行，返回 `liveStart` 40 时，缺口里第 8/15/22 行**实际到达**、被提交的两行各只一份。变异「无条件 `max`」→ 红。

**变异验证的准确口径。** 四条变异里两条转红（restore 的返回判定、邻接判定），两条不转红（park 不覆盖旧 pending、按 frame 换算下标）。不转红的原因是现有输入没有覆盖到那两条守卫，**不是**它们无效。此前我把「park 空操作不红」解释成「park 未覆盖」也不准确：若真移除整套 park，restore 分支不可达、推进随之消失，测试同样会红。准确说法是：**区分「去掉 snapshot 复制」与「去掉保存 transition」需要分别做**，本轮没有分别做，所以该结论暂缺。

**再一轮：两个跨帧缺陷与一个来源判定漏洞。** 三条都属实。

1. **「未知时 snapshot 保留」与落盘不符** —— 属实，之前的 restore 无条件清空 snapshot，随后 browse 又用新窗口覆盖，等于把未知结果丢掉。现已区分**「尚未解析」**与**「解析为没有」**两个状态（`#parkedUnresolved`），前者保留 snapshot 等下一个带正文的帧解析。测试延长为跨帧：browse 返回（未解析）→ 返回完整文档 → 再增长；被终端提交的具名行不额外增加，**同时缺口里的行必须到达**。变异「每帧都清」→ 红。

2. **已知 credit 被过早退休** —— 属实，是差集修法带来的新缺陷。原来在求差前就清掉整个待扣除区间：`liveStart` 8、`credit=[20,22)`，返回同一份文档同一 `liveStart` 时 `floor = candidate = 8`，本帧根本没提交到 20，却把 credit 清了；随后增长越过 22 时 20/21 会被**再提交一次**。现在**只退休本次结算真正覆盖的部分**，超出 candidate 的部分继续挂起。测试按复核给的输入写。变异「无条件清」→ 红 2 条。

3. **frame 来源判定两处越界** —— 第一处已修：`documentRows === undefined` 现在表示**来源未知**，不再是「整份文档」；`null`、未知、已知区间三者分开。第二处**修了代码但没有回归守护**：换算下标前先检查 document 是否落在 `[documentStart, documentEnd)` 内，因为 `next` 还含 composer/footer，正文区间外的 chrome 不能用来确认正文 credit。变异「undefined 当整份文档」→ **不红**：`frame()` 辅助函数总是声明区间，所以只有手写的无区间帧会走到那个分支，而那种输入下 credit 两种算法都是「未知」，结果一致。要真正区分需要一个「无区间帧恰好覆盖到待核对行」的输入。

**park 守卫的变异口径（按复核建议区分）。** 「不覆盖旧 pending」其实是两个条件：**没有新 transition**、以及**已有 main pending**。普通 overlay 重绘只验证前者；仅删 `mainResize === undefined` 在没有新 resize 的输入上本来就等价——要测后者需要**第二次真实 resize**，并明确每次几何变化都保存与结算，不能只以布尔守卫存不存在作证明。本轮没有做第二次 resize 的输入，所以该守卫的**后半**条件仍无守护，已如实记下。

**再一轮：三个问题，其中一条是我上一轮引入的回归。**

1. **未解析时整个返回帧被吞 —— 属实，是我上一轮引入的**。为了让 snapshot 存活，我在 paint 之前 `return`，于是**browse 根本没画、1049 根本没退出，用户仍看着 overlay**。原测试只查历史，而最终历史是对的（下一份完整文档解析时才退出），所以**中间那帧显示错了却被掩盖**。

现已按你说的把三件事拆开：**是否可以画主屏**、**自然搬行事实**、**当前正文核对是否完整**。park 的 snapshot 收进独立的 `#mainResizeRecord`，结算不再阻塞绘制；重试入口也不再依赖 `altActive`（真实退出后 `altActive` 为 false，靠它就再也读不到那份记录）。两条测试现在在 render 之后**立即**断言 `altActive === false` 且请求的窗口确实在屏上。变异「未解析就 return」→ **红 2 条**；变异「重试只看 altActive」→ **红 2 条**。

2. **「未知」与「已知没有」仍未分开 —— 属实**。原来只有 `credit === undefined` 一个信号，而 helper 对 grow、`pushed = 0`、来源未知、文本已替换**都返回同一个 undefined**。你给的最小输入（H10 光标在物理 row0 → alt → 同宽缩到 H8 → 返回完整正文）自然推行数确定为 0，却被当成 unresolved，此后**每个主屏帧都持续重新打开它，界面永久卡在 overlay**；变高同样会触发。

现已新增 `#creditAgainst`，返回 `{ confirmed, remaining }`：`confirmed` 是本次能确认的区间，`remaining` 为 `'unresolved'` 才表示**尚不能核对**。`pushed === 0` 现在明确返回**「已解析、结果为空」**而不是未解析。行为测试：零推行输入下比较必须**了结**、overlay 必须退出、后续增长正常且无重复。变异「零推行当未解析」→ **不红**，原因见下。

3. **部分可见窗口丢掉剩余自然提交 —— 属实，已修**。`documentRows=[20,21)` 只显示一行时，helper 确认 20 后在 21 越界处 `break`、返回 `credit=[20,21)`，restore 随即当作**全部解析完**清掉记录；后续完整 follow 增长只扣 20，**21 会被主动再交**。现在结果携带「已确认区间 + 尚未核对余项」，余项留在独立记录里等下一帧。

**关于「零推行当未解析」这个变异为什么不红。** 它要成立，需要一条**先因来源未知而打开比较、随后又以零推行到达**的输入。我试过用「无区间帧返回」制造前者，但零推行的判定在 `#creditAgainst` 里**先于**来源检查发生，所以那一步直接返回「已解析为空」，`parkedUnresolved` 从未置真，变异路径根本不可达。换句话说：**这个变异在当前代码里是不可达的，而不是被测试覆盖了**。真要覆盖需要一个「零推行且来源未知」的顺序，目前 helper 的判定顺序让那不存在——这本身值得复核，但我没有把它算作已覆盖，已如实记下。

**覆盖口径的更正。** 我上一条写「第一处修完、第二处无守护」，随后给出的不红变异却是 undefined 当整份文档（**第一处**），标题与证据说反了。准确说法：第一处（`undefined` = 来源未知）**有**行为测试与断言；第二处（先判正文区间再换算）代码已改，但**仍无守护**——现有无区间用例 `slice(0,8)` 确实没覆盖待核对行。按你的建议，下一步会补两个输入：①用完整 `all` 但省略 `documentRows`，并先锁住请求画面真实出现，再提供有来源的正文结算；②正文区间**之后**的 chrome 恰好与旧正文同文本，锁住 `documentEnd` 判断。

**再一轮：三个跨帧丢账路径，以及我上一轮对「变异不可达」的错误解释。**

**校准结果（该夹具中，grow 之后、任何 paint 之前直接读终端）：**

1. `added` 那条拿 **grow 之前**的 frozen 快照来禁止后续提交——快照里包含已被拉离历史的行。

**仍未做**：`position.document` 仍是推送时的旧布局行号，reflow 之后直接 `min(#physical, position.document)` 并不精确（物理位置顺序与「映射到当前文档」是两个维度，后者需要布局身份或明确未知）；`pull` 把原始 `shown`/来源放回**隐藏布局**（修驻留内 grow→shrink）；可见确认点的 B 构造；38/39 与 A=36/37 的精确夹具；来源/chrome 守护。

**剩余失败**：仅「非纯推行之后没有可恢复来源」一条。

**再一轮：两处测试证据补正。**

1. **回答用例的 pull 前提此前只有文字、没有断言。** 注释写着「直接测到 `answer line 1` 在屏上、不在历史」，代码里并没有这些断言，而且 `beforeGrowth` 是取在 **paint 之后**。更要紧的是：**pull 发生在终端自己的 `resize` 里**，所以快照必须取在 `emu.resize` **之前**——取在之后已经能看到行回到屏上。

实测确认：把 `mapBlockSpan` 强制改成**总选第一个块**，这条用例**仍然通过**。所以它**不再区分选块规则**，本轮把它如实**重新定位为「提交结果的护栏」**——保证边界从历史实际所在处继续、既不重放已冻结的也不跳过答案中段；选块规则由 `mapBlockSpan` 的**纯函数用例**承担，不再在这条上声称杀死了哪些变异。

**隐藏布局恢复：本轮尝试并回退，未落地。**

**结果：引入了回归。** `accounts for two resizes within a single overlay stay` 由绿转红——同一驻留内的第二次 resize 拿不到正确布局，其自然提交无法入账，那些行被重交。我把布局前移从「结算时」搬到「park 时」（几何与弹出位置在那一刻才已知），回归**依然存在**，说明问题不在时机，而在我对「第一份记录的布局」与「后续记录应基于哪一份」的衔接上——`sourceUsable` 的判定与布局的存活期没有对齐。

**没有把它留在半成品状态**：已整段回退到上一轮的绿状态（134 过、1 红），并把尝试的经过记在这里，而不是留一个「看起来更完整」但带着回归的实现。

结论收窄为：**这一维需要先把「布局存活期」与「`sourceUsable` 判定」对齐**（即：一份布局属于哪一次移动、在什么条件下失效），再谈前移与恢复；这与我此前记录的**第二维**（`position.document` 是推送时的旧布局行号，reflow 后不能直接当当前坐标）是同一处身份问题。

**隐藏布局：共同移动操作与 before/after 链已落地。**

按复核给的生命周期设计实施（同宽、逐次 resize 范围内）：

1. **物理效果移到 park 时执行一次**（`#applyMove`）。此前 push/pop 在**结算**时才做，而同一驻留内的下一次移动在那之前就 park 了——它读到的尾部**还没有移动过**，取到的是错误的实例。现在移动在 park 时就落到尾部上，后续移动看到的是它真正留下的历史。

2. **每份记录带自己的 `after`**，作为下一次移动的 `before`（`before = earlier?.after`）。此前是**从队尾记录重新推导**（`advanceSnapshot`），那会退回一整步、跨过其间发生的事；而 live 字段则会退回整个驻留。10→8→6 现在是 20..29 → 22..29 → 24..29，两条记录的 `before` 分别是 20..29 与 **22..29**，第一条不会被就地改成第二条的 before。

3. **pull 把弹出实例的 `shown`/`document` 放回布局**（`record.after` 的构造），所以驻留内 grow→shrink 之后的移动拿得到可读来源，而不是退回 live 字段。

实测：**134 过、1 红，无一回退**；`accounts for two resizes within a single overlay stay` 保持绿。`describesLayout` 与 `advanceSnapshot` 两条旧路径已随之删除。

**仍未闭合**：唯一那条红（`does not settle a move whose layout is unknown as if it credited nothing`）仍是红。复核给的另外几点尚未做——`currentNormal` 的**物理版本**与**文档投影版本**两个身份分开表达、未知来源在行级保留（而不是整份几何失效）、旧 projection 需要显式映射后才可改 `#physical` 或生成 credit。另：`position.document` 仍是推送时的旧布局行号，reflow 后不能直接当当前坐标。

**全部已知缺陷闭合：1266 条全绿。**

复核指出的三处几何错误都属实，修完后唯一那条红转绿：

1. **grow 的 `after.cursorRow` 没有随拉回的行数增加。** 首次 shrink 后 cursor=5，grow 拉回 23 后应为 **6**，原实现仍记 5 —— 于是下一次 `7→5` 只按 1 行计算，而终端实际推了 2 行（23/24），24 未入账、返回后被重交。现在 `after.cursorRow = min(cursor + taken.length, newHeight-1)`：**拉回的行把光标一起带下来**。
2. **移动决策与移动快照取自不同的前态。** `pulledBack` 用 live 的 `#cursorRow`，而记录用 `before.cursorRow` —— 而驻留期间 live 光标仍是**驻留之前**那块屏的。现在统一为 `moveCursor = before?.cursorRow ?? #cursorRow`，推/拉数量与 `after` 都用它。**不能拿 live 光标判断隐藏屏是否在底部。**
3. **`after` 必须完整描述 `newHeight`。** 无 pull 的 grow 原先只 slice 旧数组、没补底部空行；`taken` 少于请求数量时也不能伪装成完整已知布局（现返回 `undefined`，明确未知）。**已知新增的空白可以补齐，来自未跟踪历史的内容必须标为未知**，不能用普通空串替代。

另外两点也按复核改了：**宽度变化不再自动 `sourceUsable: true`**（未建模的形状仍应明确未知）；`#applyMove` 目前仍只覆盖 parked 路径，**可见路径仍有自己的 push/pop，「共同」尚未覆盖两条路径**——这一点记在未完成里，避免两边 grow 光标规则再次漂移。

守护：光标增量这一条有变异守护（去掉增量 → 红）；`moveCursor` 取 live 与 `after` 补齐这两条**目前不红**，因为现有输入下二者的差别未被观察到。测试现在在**每次 resize 之后、paint 之前**锁住终端的 normal 光标（5 → 6 → 4），把 `after.cursor` 与真实屏幕对应起来。

**仍未做**：可见/隐藏两条路径合并到同一个移动算法；物理版本与文档投影版本分开表达；未知来源的行级保留；旧 projection 的显式映射；`position.document` 的当前坐标映射；38/39 与 A=36/37 的精确夹具；来源/chrome 守护。

**未知几何的传递：规则已落盘，但该状态链仍失败。**

复核指出的传播路径属实：`earlier.after` 不存在时退回驻留前的 live 快照、`sourceUsable=false`，而 `#applyMove` **不检查这份几何是否可信**，仍生成一个有值的 `after`；下一次 park 只检查 `before !== undefined`，于是**重新得到可信**。这是「未知 → 猜测 → 已知」的错误传播。

已按复核的修法分开两件事——**物理几何可信** 与 **正文来源可用**：

- 新增 `geometryTrusted`，**继承而从不从「值存在」推断**：一份记录若建立在未记账的屏幕上，它产出的 `after` 本身就是猜测。
- `#applyMove` 在起点不可信时**不构造 `after`**（而不是构造一个看起来完整的），所以后续移动继承的是「未记账」而不是猜测。
- **宽度变化**同样置为不可信（未建模的形状），不再因「总能构造出 after」而被当作已知。
- 没有对所有 `sourceUsable=false` 早退：屏幕**已知没有正文**时仍有真实的物理移动，那部分照常记账。

**但这条状态链仍然失败，因此标记为已知缺陷而非已修。** 复核随后给出了直接的静态解释，并纠正了我据此做的推断：

- 宽度记录没有 `after`，于是后两次 shrink 的 `sourceUsable` 都是 false；`#creditAgainst` **永远返回 unresolved**，完整正文也恢复不了这几份记录。没有确认任何 credit，返回 follow 就退化为「从 `physical` 到 candidate 的普通 flush」，把终端已自然提交的行再送一次。
- 所以成因是**「阻止了错误的恢复，却没有实现正确的抵扣」**，不是「另有一个无关的 bug」。
- 我此前写「把 `geometryTrusted` 恒为 true、失败完全相同，所以传递规则与重复无关」——**这个推断是错的**：一个变异没能让失败的用例转绿，**只能说明该变异不足以单独修好它**，不能推出它与该缺陷无关；而且宽度分支的早退、`sourceUsable` 的独立条件当时都还在。

**修法也已按复核收紧两处**：(a) 新增 `outputTrusted`——「移动**之后**的布局是否可信」是独立事实，不能由「起点可信」继承，也不能仅凭 `after` 存在来判断；尾部不足的 grow 现在把输出标为不可知，下一次继承的是它。(b) `#applyMove` 的信任检查**移到账本改动之前**——原先先按旧 cursor/source 做了 push/pop 并回退了 `#physical`，后面的 guard 只拦住 `after` 的构造，**没有拦住这些猜测已经改了账本**。

**下一步按复核缩到该夹具**：`setWidth` 只记录宽度、不模拟折行，`line-N` 都是短行。把原始输出序列交给 headless，返回 paint 前锁住 normal 的原始新增历史、整屏与光标，确认这个短行输入里**哪些来源确实保持不变**，再为**可证明**的行保留来源并结算；真正发生折行的宽度输入继续明确未知，**不用本夹具推广**。同时补上「尾部不足 grow」的输出可信传播守护。

其余两点也按复核改了：测试的 5→6→4 断言移到每次 `resize` 之后、`overlay` 之前（此前在 paint 之后，与注释所说的时机不符）；源码里引用已删除的 `advanceSnapshot` 的两处注释、以及「push/pull 留到结算」的旧说法都已更正——push/pull 现在在 **park** 时执行。

**输出可信的守护没做到。** 按复核要求补的「尾部不足 grow 之后，输出不应被当作可信」用例**落盘了，但它不承重**：把继承改回「沿用输入的 `geometryTrusted`」，该用例**仍然通过** —— 说明这个序列没有走到尾部不足那条路径。规则在代码里、也按复核的理由成立，但**这条用例不是它的守卫**，测试注释里已如实标注，不当作已覆盖。

**再一轮：尾部可信范围、以及「短历史≠短尾部」的输入前提。**

1. **「新夹具为什么不触发尾部不足」这次算清了**（复核给的数量证据）：初次渲染记下它自己 flush 的 8 个位置，两次缩高又推入 6+1 个，两次 grow 只拉回 2+3 个 —— **尾部始终够长**，那条路径根本没进。所以「短文档」不等于「短尾部」；我上一轮只用「变异仍绿」推断路径未进，依据不足。

**保护动作的诊断起点被复核纠正：覆盖不一定是 `2J`，而「差额」也不是外部行数。**

我上一条把诊断写成「先查清哪一次调用发出 `2J`」，**范围错了**。复核按代码给出的两条覆盖路径都成立，我逐一核对：

**（2）「差额就是外部行数」不成立。** `pulledBackFor` 返回的是**允许拉回的上限** `newHeight - oldHeight`，它**不知道原生历史实际有几行**。对照实测：altShell 请求 10，实际只拉回 **9**（3 条自有 + 6 条外部），按 `10 - 3 = 7` 已经**多算 1**；visibleShell 请求 5，实际拉回 **4**（3 自有 + 1 外部），`5 - 3 = 2` 同样**多算 1**。更极端的情形是**没有任何外部历史、只有 3 条自有历史**时 grow 10 实际只拉回 3、其余补空白，而同一个「差额 7」会**误报存在外部内容**。

**渲染器看不到 headless 的 `baseY`**，不能把探针知道的实测数量当成生产事实。现在能识别的只是「**可能**越过了已知尾部」，**不是精确的未知行数**。所以保护策略必须**处理这个不确定性**：直接按差额滚屏不仅可能滚错，还可能**把已知的自有行再推一次**。

**保护实现的前置结论：当前终端接缝没有保护所需的能力。**

按同意的方式准备接入最终绘制计划（覆盖 `CUP`+`EL` 与 `2J` 两支、退出 1049 先于保护、保护产生的物理顺序同时入账）时，先确认了保护动作能拿到什么信息，结果是一个决定性的事实：

**`provider-local.ts` 的 `Terminal` 接缝只暴露 `width()`、`height()`、`onResize`**（`:273-278`），**没有任何缓冲/历史状态**。渲染器拿不到 `baseY`，**provider 同样拿不到**。而校正过的口径已经确认：渲染器只能识别「**可能**越过了已知尾部」，**不能**算出外部行数（`pulledBackFor` 是请求上限，实测请求 10 实际只拉回 9）。

于是保护动作缺少它必须有的那个输入：

- **要滚几行**才知道把外部行推回历史？——渲染器不知道，provider 也不知道。
- 按请求上限滚：会**多滚**，把已知的自有行也推进历史（这正是成对对照要防的）。
- 不滚、照常覆盖：外部行丢失（当前红用例）。

**所以这不是「换个接入点」能解决的**，而是需要二选一：

1. **扩大终端接缝**：让 provider 能读到终端的光标行/历史行数（`baseY`），渲染器据此精确知道外部行数；这是**跨层的接口变更**，需要 provider 与渲染器一起改。
2. **避免进入该状态**：不让终端出现「拉回的未知行停在屏上、随后又要被覆盖」的局面——例如在进入 alt 之前先把隐藏主屏处理到不会被 grow 拉回的位置。复核早先提出的「进 alt 前停放光标」属于这一路，**但已由可见路径证明覆盖不了全部形状**，需要先弄清它在可见路径上还缺什么。

**两条都未实施。** 我没有把「按上限滚一行试试」写成保护——那正是被校准否定的做法。

**写侧保全候选：实测出一个冲突，按复核的要求如实上报。**

按复核给的候选实现了一版：在**最终绘制计划之前**（`CUP`+`EL` 与 `2J` 两支都接上）先 `CUP` 到当前屏底、按**完整屏高**把整个可见快照滚出，再执行绘制。它不读、不重放未知文本，也不把请求差额当成外部数量。

**外部行确实被救回来了：**

| 序列 | 之前 | 加上保全之后 |
| --- | --- | --- |
| `altShell` 外部六行 | 最终返回帧全部消失 | **最终仍在，六条各一份** |

**但同一改动让自有行出现重复**，正是复核预告的反例：

| 序列 | 自有行最终份数 |
| --- | --- |
| `altShell` | `line-0x2, line-1x2, line-2x2` —— **各多出一份** |
| `noExternalShell` | 同上，**各多出一份** |

我试过把保全滚出去的实例**标记为已抵扣**（按屏幕上的实际文本构造确认，`credited: true`、`text: shown`），**重复依旧**——说明这些行不是通过 ledger 的抵扣路径再发的，而是**最终 flush 仍从 0 无条件提交了同一批**。这正是你说的「保护导致的移动要作为独立物理事件处理」，而我只做了「记账」这一步，**没有把 flush 的提交范围也扣掉它**。

**结论：这个候选的两个目标在当前实现下冲突** —— 保全外部快照会让自有行多出一份；把它们标记为已抵扣不足以解决。**已整段回退**（不是留一个会产生重复的实现），回退后 `138 过、1 红`，与尝试前一致。

**关于接缝**：按复核更正，`baseY` 是持有 xterm.js 实例时的 `IBuffer` API，**不是普通进程连终端时现成可读的状态**；CPR 只能查行列、推不出历史行数。所以**不先加一个只能由 headless 测试实现的 `baseY()` 接口**。

**「产品取舍」这个说法已撤回。** 复核说得对：我证明的是**当前组合实现重复**，不是两项目标不可兼得；而且复核指出的绕过也确实存在——差集只在 resize 分支里做，普通增长那条仍直接 `#paintFlush(physical, candidate, …)`，**保全挂在最终字节串之前时 body 早已选定**，后来写账本当然不会重算那段字符串。

**按复核给的目标重做了一版**（同宽、单次 grow、不改文档）：顺序改成**绘制计划**——先选定原待提交区间 → 计划保全 → 记录保全能证明的自有实例 → **算区间差集** → 最后一次生成字节；`noteFlushed` 只记实际剩余区间。目标区间按复核算得也很清楚：原待提交 `[0,25)` 减去保全证明的 `[0,3)` 与 `[25,30)`，**只剩 `[3,25)`**；`[25,30)` 超过本帧 candidate，必须留给后续增长继续抵扣。

**仍然重复，而且这次找到了确切的卡点：**

```
PLAN {"screen":["line-25","line-26","line-27"],"src":[25,26,27],"pushed":0}
```

`#planProtection` 在保全点看到的 `#screen` / `#screenRowSource` 是**渲染器自己上一次绘制的内容**（`line-25..27` ← 源 `25..27`），**不是终端此刻真正的屏幕**（那里是 `shell-0..5`、`line-0..2`、`line-25..29`）。所以它把**错的那些行**记成「已被这次滚屏提交」：`confirmed` 得到 `[25,28)`，而真正被滚出去的是 `line-0..2` 与外部行 —— **它们没有进入差集，于是 flush 照旧从 0 提交，重复照旧**。

**这不是差集接得不对，是「保全滚走了哪些行」在渲染器里无法确定**：它的屏幕记忆是**自己画过的**，不是终端的。这与 `tailStale` 是同一类缺口——渲染器缺终端状态。**已整段回退**，回退后 138 过、1 红，与尝试前一致。

**复核纠正了这个结论的因果，我接受：缺的信息一度就在渲染器手里，是 grow 处理把它丢掉了。**

- `line-25..27` **不是「错的行」**——在本次同宽单次 grow 里它们确实仍在终端屏上，整屏保全也确实会把它们滚入历史。错的是**把这份部分集合当作全部**：漏了被拉回的 `line-0..2`，也漏了原屏的 `28/29`。
- 真正的丢失点在 `#applyMove`：`const taken = #pushed.splice(-pulled, pulled)` 之后，`taken` 就带着 `line-0..2` 的**实例、`shown` 与来源**；一旦 `taken.length < pulled` 就 `record.after = undefined` 返回，**这份集合既不在栈上也没存进记录**。可见路径同样把 `splice` 结果直接交出去、未保留。所以 `PLAN.pushed=0` 不是「从来不知道这三行」，而是「知道之后移出了栈、后续计划拿不到」。
- **关键区分**：完整几何未知，**不等于所有实例的存在性未知**。在限定输入里，可信尾部有 N=3 个已跟踪位置，同宽 grow 在旧屏底、允许拉回 K=10，**实际 pull 必然包含这三个最近的实例**；原屏那五个实例在单次 grow 中也都保留。整屏保全时这八个实例必然全部入历史——**无需读取未知文本**。

**按此重做后：**

- `#applyMove` 把 `taken` 存进 `record.pulledRows`，**即使 `after` 未知也不丢**；并把「确定仍在屏上的自有实例」收进 `#knownOnScreen`。
- 保全计划**消费这份实例集合**（带旧的文本与来源），而不是 `#screen` 的旧物理下标，再做上一轮的差集。

**实测结果：**

| 序列 | 自有行重复 | 外部行存活 |
| --- | --- | --- |
| `altShell` | **无** | **六条各一份，最终仍在** |
| `noExternalShell` | **无** | —（无外部行） |
| `visibleShell` | **无** | 仍丢失（该支未接入保全） |

也就是说**保全集与「自有行零额外重交」在 alt 路径上已经同时成立**——我此前说它们冲突是错的，回退时把它当成不可兼得也过早了。**`visibleShell` 那一支仍未闭合**：它的自有行不再重复，但那一条外部行还是没保住。

**复核随后指出四处缺口，我核对后确认三处仍未做：**

1. **保全只有一个调用点**（普通增长分支）。可见 grow 走前面的 resize 分支，仍直接 `paintFlushRanges`；transient 返回等其它主屏覆盖也没接。**所以 `visibleShell` 丢行不是实例语义失效，是接入范围不完整。**
2. 初版 `#knownOnScreen` **只收 `taken`，没收原屏那五行**，所以「据它确认 `[25,30)`」当时**并未落地**（此前那句已更正）。

`text = shown` 那一步的**准确范围是「已保存旧快照文本、后续文本比较有了输入」，不是「本帧确认正确」**：`#planProtection` 当时不接收 `next`/`frame`，直接把每个 `document` 放进 `confirmed`，**这一帧的差集是无条件跳过的**，后来的 `creditedRows` 比较救不了它。复核给的最小输入成立——同宽单次 grow，返回的完整文档把 `line-0` 改成 `replacement-0`：保全仍保存旧 `line-0`，而 `replacement-0` **必须主动到达**，不能被 `[0,3)` 一并扣掉。

已补：生成 `confirmed` **之前**按有效来源映射核对**当前文本**——相同才扣，不同不扣，无法映射记为未知；**实例仍然保存**（它确实被滚走了），保存与「当前抵扣资格」**不再绑在一起**。新增行为用例（改写首行）并做了变异验证：去掉文本核对 → 该用例**转红**。

另按复核更正范围：**「grow 保留原屏实例」目前只在 parked 一侧**（`#applyMove`）；可见分支仍只 `push(...taken)`。而且新循环读的是 **live 的 `#screenRows`/`#screenRowSource`、按当前 `#height` 遍历**，**没有读该事件自己的 `record.screen`/`rowSource`** ——这只在「首次、无中间移动的 grow」里等价，后续事件不能拿 live 旧屏当本事件前态。**按事件自身来源收集**这件事仍未做。
3. **触发条件与生命周期未成立**：`#unknownOnScreen` 只置真、从不消费或复位；`#knownOnScreen` 只在 `planProtection` 清空，**真实主屏 paint 或后续移动时不会更新/失效**——可见那帧覆盖屏幕后，旧集合会留到后来的普通增长，届时它已不能证明「这次保全滚出的行」。入口按 `knownOnScreen.length === 0` 跳过保全，还会**漏掉「只有未知外部快照、没有可辨认自有实例」**的情形：**是否需要保全应来自尚未处理的风险事件，与「有没有自有 credit」是两件事，不能共用一个非空判据。**
4. **物理尾部不能退回稀疏账本**：整屏保全真实推了 H 个位置，而计划只把可辨认的几行追加进 `#pushed`，尾部仍被当作精确可 pop；外部位置、原屏五行、空白的位置都没表达，后续 grow 跨过新 flush 后缀时**仍会弹错**。`settledByProtection` 目前只写不读，挡不住它。**保全后的「已确认抵扣集合」与「可精确跟随的物理尾部范围」必须分开**，未知排列要留下明确边界。

复核另指出一处顺序问题：当前收集顺序是**原屏 25..29 在前、pulled 0..2 在后**，而真实保全顺序是**外部前缀、0..2、25..29、空白**。它作为**实例集合**没问题，**但直接按此顺序追加到「精确的 `#pushed` 尾部」就更不能成立**。已明确保留这一状态：**不拿集合顺序当物理顺序**。

成立的前提照复核算：**可信尾部、同宽单次 grow、无重画/改文档/reflow**。不能拿去认领 grow→shrink 或未知宽度移动后的行；不清全局 stale；实例携带的是**旧来源**，映射到当前正文仍需验证。

**已定位的 CUP 模型分歧：修正后两条红都转绿，但归因需要按复核重新校准。**

复核直接给出了能解释那条红，而**不需要**新增「恢复旧文本」分支的模型差异，我核对后两处都成立：

1. **渲染器发的不是屏底。** `csi(row, column)` 是**零基 + 内部加一**（`ESC[{row+1};{column+1}H`），而保全末尾传的是 `csi(this.#height, 1)` —— H15 时实际发 **`ESC[16;2H`**，靠终端钳制越界坐标才「碰巧」落到屏底。已改为 **`csi(this.#height - 1, 0)`**。
2. **手写模型没有钳制 normal 光标。** `#setRow` 只对 alt 做了 `min(height-1, row)`，normal 直接赋值；CUP 把 16 换成零基 15 后**光标真的停在 row 15（屏底是 14）**，后续 15 个 LF 判断 `activeRow === height-1` 恒为假，**没有任何一行进入 history**，最后的 EL/2J 重画自然把 `line-0` 盖掉。这**同时解释**了此前 headless 保全成功与 spec 失败的差异。已按 xterm 的 `_restrictCursor` 语义把**两个缓冲都钳制**，并**加了一条独立的越界 CUP 断言**，避免只修渲染器而把模型缺口藏住。

**修正后：`spec` 141 条全过、整仓 1272 条全过、0 红。** 此前两条红里的 `does not take its own tail…` **仍有此前的独立终端逐帧证据**；**改写首行那条则不能新增为真实终端丢失证据**（它的红由 CUP 模型分歧导致）。两条到达断言都没有改弱：旧 `line-0` 与新 `replacement-0` 各一份。

**但复核给出的准确状态必须写在前面**：这条红**已复现于手写模型，存在已定位的 CUP 模型分歧，真实终端上的归因仍待校准**——不能因为改正断言后红了就全部归到渲染器，也不能因为现在绿了就当作已证实的渲染器缺陷已修复。下一步要把这条改写序列的**真实输出**交给 headless，逐帧核对**保护后、重画前**的 history，确认模型与独立终端一致。

**仍未完成**：可见分支与 transient 返回的保全接入；风险事件/实例证据的跨路径存活与消费、生命周期失效；按事件自身来源收集；尾部未知边界；跨 30 与两路径的行为回归；H1/composer。这些**不因为现在绿板而归零**。

**改写序列的真实终端校准：此前那条「模型/终端分歧」是我读错了，已撤回。**

复核指出两处证据问题，都成立，而且第二处直接解释了那个「分歧」：

1. **合计不能代替分侧。** 我报的 `line-0` / `replacement-0` 是 **history 份数 + viewport 份数**；一行从 history 移到 viewport，合计仍是 1，所以「全程留在 history」这个结论**超出了那张表**。
2. **校准与规格不是同一输入。** spec 的夹具只写 **`shell-0..2` 三条**，而探针 `rewritten` 用的是默认 `external: 10`（十条）。grow 前历史长度、可拉回数量、grow 后光标都可能不同，**不能据此归因模型**。

已按复核改成 **`external: 3`** 并把两侧**分开报告**：

```
事件                 baseY cursor   line-0(h/s)   repl-0(h/s)
render                 3     4      1 / 0         0 / 0
render overlay(2)      3     4      1 / 0         0 / 0
terminal.resize       0     7      0 / 1         0 / 0     ← 离开 history、出现在屏上
renderer.resize       0     7      0 / 1         0 / 0
render overlay(3)     0     7      0 / 1         0 / 0
render（grown）        38    14     1 / 0         1 / 0     ← 两行各一份，回到 history
```

**同一输入下，真实终端的行为与手写模型一致**：`line-0` 在 resize 时**确实离开 history、出现在屏幕上**（`0 / 1`），末态旧行与新文本**各一份**。所以此前那句「真实终端里 `line-0` 全程留在 history、中间态是模型侧分歧」**是输入不匹配造成的读数错误，已撤回**——这里没有新的模型缺陷。

**观察点也按复核算清**：「resize 后、任何 paint 前」的位置**能从现有事件读数直接检查**（上表就是这样得到的），与「保护与重画之间取不到状态」**是两个不同的观察点**，不再混用。

**四项交付边界：第 1、2 项已落地，跨路径保全现在三条序列都成立。**

按复核锁定的边界实施：

1. **触发改由「尚未消费的风险事件」决定**，不再看 `#knownOnScreen` 是否非空——只有未知外部行、没有可辨认自有实例时同样需要保全。`#planProtection` 现在按 `#unknownOnScreen` 触发，消费后立即清掉。
2. **两条覆盖主屏的绘制计划共用同一入口**：普通增长分支与 candidate 分支都调用同一个 `#planProtection`，再按**当前正文核对证据**、求差、生成实际字节；candidate 分支不再自带一套逻辑。
