# 设计哲学

omdsh 是 DeepSeek Harness 的终端。这份文档规定 omdsh 该做什么、不该做什么，以及做判断时依据什么。

优先级：`AGENTS.md` 是仓库的强制规则，本文是它的理由与展开。两者冲突时，以 `AGENTS.md` 为准，并修正本文——一份说明理由的文档不能否决它所解释的规则。本文优先于 `docs/design/` 下的其它文档，那些是它在具体领域的应用。

## 底座与消费者

DeepSeek Harness 拥有 agent、session、tool、policy、permission 和事件日志。omdsh 拥有终端呈现与输入。

dsh 的架构文档在"新行为该挂哪"的表里，把这样的集成描述为 `drive ctx.agents` and render from `session/event`。那一行讲的是**挂载点**，不是职责边界；把它读成后者是本项目的推论。推论的理由是：一旦 TUI 自己记录会话事实，日志就不再是唯一来源，而 resume、回放和 fork 都以日志为准。

边界不在于谁起草内容，而在于谁记录它。TUI 当然起草内容：composer 拼出粘贴文本、`@` 引用和附件，`/btw` 组织提问。这些都要跨过入口才成为会话事实。因此：

- **跨过入口后，`SessionEvent` 是唯一事实来源。** 提交、inbox 排入、`agent.inject()` 都是 Harness 入口；一旦通过，模型能看到的内容只能从日志回放。TUI 可以补充只有终端才知道的事实（粘贴的字面意图、视口位置、终端能力），但不能让一份内容只存在于自己的内存里。
- **一份内容不能有两个来源。** 同一段内容既注入会话又写本地转录，会让模型记得而转录在 resume 后缺失。这正是本项目出现过的一类缺陷：`form: 'notice'` 的插件注入曾经只画在实时视图里。投影必须识别会话里已有的内容，而不是并列地再写一遍。
- **TUI 拥有提交前的意图，以及它的持久化。** 草稿、输入历史、排队中的消息属于 TUI，它们最终会成为会话内容但此刻还不是。规则是：跨过入口必须是单点、可见的动作；入口前的内容在转录里必须标明尚未提交。
- **TUI 不重新实现 Harness 的能力。** 权限判定、沙箱、审批规则、任务调度、反馈记录由已发布的包拥有。TUI 是这些服务的一个人机入口，不是它们的替代实现。
- **投影可以丢失，事实不能伪造。** 折叠、截断、预览都是呈现决定，读者随时可以展开回完整内容；反过来，把"没有收到结果"显示成"成功"是禁止的。

这条边界的实际含义：当一个问题看起来需要 TUI 自己维护状态才能解决时，先问它是投影问题还是事实问题。投影问题在渲染层解决，事实问题必须回到 Harness。

## 结构原则：核心只拥有不可委托的东西

dsh 的主张是"没有特权核心，一切挂载在旁"——它回答的是**放在哪**，不限制功能多少：DeepSeek Code 本身就是大量插件组合出的完整产品。

omdsh 因此把核心限定在不可委托的部分：

1. **终端所有权。** 谁在什么时刻拥有 tty、哪些模式被开启和归还；同一时刻谁接收按键，叠层如何抢占与归还。按键归属和 tty 模式一样不能被插件协商。
2. **呈现调度。** 把 Harness 的投影变成终端帧：转录行、常驻 chrome、以及它们越过原生历史边界的时机。投影内容可以按插件分片，但"下一帧画什么、哪一行冻结"必须有一个所有者。
3. **文档替换。** `/clear`、resume、fork 在带标签的边界之后追加新文档。历史契约依赖这一动作，插件无法安全地实现它。

`ctx.tui.prompt` 不在这三项里：它是服务契约，审批的裁决权在 Harness 的 permission service。TUI 提供的是渲染与按键，不是一个核心独占的交互。

这个服务契约本身也说明了另一件事。`TuiPrompt` 曾是**一个**被 196 处调用的接口，长到 46 个可选字段：每加一个新界面就加一两个字段（`presentation`、`optionLayout`、`filterable`、`approveValue`、`wait`、`interrupt`……），调用方各自组合出自己的一套。结果是没有哪个字段能说清"哪些字段属于一起"，而"功能堆砌"就是这样在接口层面发生的。

`src/prompt-intents.ts` 把实测出的四种意图（`ask` 自由文本、`choose` 列表、`confirm` 是否、`read` 文档）写成窄函数，各自编译成 `TuiPrompt`。`ctx.tui.prompt` 保留为逃生口，给那些真正需要多个字段组合的面（审批、问题、队列编辑）。判据是：**一个调用方如果需要两个以上意图的字段，它就不是某个意图，而是第 46 个字段的来源。** 遇到这种情况先问它是否该拆成两次交互，再考虑用逃生口。

**核心之外一律是插件、服务或消费者：**

命令、设置界面、工具呈现细节、外部集成、副智能体巡览、模型推荐、审核规则入口。它们通过 `ctx.commands`、`ctx.tui` 契约或事件挂载，卸载时随 Cordis effect 回退。

## 范围原则：新能力要拿出读者需求的证据

这一条来自 pi，dsh 推不出它。pi 说核心必须小到能被扩展影响，理由是**可扩展性**；它同时主张产品本身少带东西，那是**产品克制**。omdsh 借用后者，并承认它是一条独立判断，不是架构推论。

判断一个新能力该放哪，按顺序问：

- 它是否是 Harness 已经拥有的能力？→ 做成那个 service 的人机入口。
- 它是否只影响呈现？→ 放进渲染层，不要新增状态。
- 它是否需要自己的生命周期、可能在别的宿主里也成立？→ 独立 plugin。
- 读者会不会在没有它的情况下走一条明显更差的路？→ 是，才进核心或默认插件；否，做成可选插件或不写。

**这两条原则会冲突，冲突是真实的。** 按结构原则，`/files` 有独立生命周期，应该降级成可选插件；按范围原则，它的需求已被 `@` 补全、工具路径动作和回合的 Changed files 覆盖，所以它被删除。两个结论不同，因为回答的不是同一个问题。遇到这种分歧，选**范围原则**：一个没人需要的插件，挂在那里只是维护成本。

本项目实际走的是 dsh 式的组合路线（[上游功能支持盘点](../../docs/integrations/upstream-feature-support.md) 列了 36 项能力条目）。按 pi 的克制标准，其中不少应当"默认不做"。这不是矛盾，是 omdsh 的取舍：底座能力铺开，交互入口收敛。

## 单一投影原则

**每份会被覆盖的展示状态有一个所有者；其他路径只能提交意图，由所有者用一个转换函数裁决；异步结果必须带代次，过期结果直接丢弃。**

这条规则不能写成"一个状态只有一个写入方"那样的通用禁令。项目里有多类状态天然有多个写入方，那是对的：

- **只追加的日志。** transcript 由事件投影、notice、命令输出和边界标签共同写入，契约是保持全序、只追加。
- **共享面板上的独立字段。** 状态栏的模型、Git、遥测来源各不相同，正确形态是每个字段一个写入方、面板只负责合成。
- **输入焦点与叠层栈。** prompt、审批、补全菜单、队列编辑会互相抢占，请求方天然有多个，需要的是一个仲裁者而不是一个所有者。
- **取消与中断。** Ctrl-C、`AbortSignal`、会话切换都能结束同一个运行，语义是幂等的"任一触发即终止"。

规则管辖的是剩下那类：**会被下一次结果覆盖的展示状态**。

规则的后半句和前半句同等重要，这是从一次故障里学到的（[附录](#附录)有原始记录）。只把所有者合并成一个并不能修好它：同一状态有多个异步来源而缺少代次判定时，最后到达的结果总是获胜，所有者再唯一界面照样会闪。

## 呈现让位于内容

终端空间和读者注意力都是稀缺的。每一行 chrome、每一个提示、每一个模式，都要证明它换来的信息大于它占用的位置。

具体推论：

- **不重复。** 模型与推理强度已经在状态栏，header 不再显示。权限级别已经在 composer 边框右角，不在别处重复。
- **常驻提醒要过两道检查。** "猜不到"是主观且随用户背景变化的，不能当判据。两道都满足才值得占一行：**不可发现**——界面里没有别的路径会让读者撞上它；**不知道就有实际损失**——不知道它会走一条明显更差的路。`Esc` 过不了第一道（运行中想停，第一反应就是按它），`!` 两道都过（没有任何菜单会引导到它，不知道它就会让模型代跑 Shell）。满足后仍应**渐进披露**：读者用过一次，这条提醒可以消失。
- **状态以颜色为首要信号，但不是唯一信号。** 工具卡片的进行中/成功/失败用同明度三种色相区分，读者不必读标签。但这不是无条件成立的：实测 16 色浅色主题会把进行中与成功的底色压到同一个 SGR 码（`47 47 45`），无色模式下三者为空，色觉障碍也不可靠。因此每个靠颜色表达的状态都必须另有文字或字形兜底，颜色只是让读者更快。
- **模式必须可见。** 任何改变提交含义的状态（Shell 模式、审查模式、被检视的子会话）都要在读者动手之前可见，而不是提交后才知道。
- **不把交互折叠成记忆题。** 需要选择时必须支持键盘选择，不能渲染一个编号菜单然后只留 composer 作为唯一入口。

## 原生历史是契约

终端自己的 scrollback 是历史，越过边界的行是**当时**的展示快照。折叠一个已完成的 run、一条工具调用落地、一次宽度变化，都不改写那些行。

这条契约有一个直接后果，也常被误认为缺陷：历史里的旧块与当前实时视图不同。那是预期行为。唯一允许的分界是显式的文档替换（`/clear`、会话切换、resume、fork），它在带标签的边界之后追加新文档，并保留此前的输出。

配合这条契约，呈现必须增量：已定型的行缓存，滚动和流式 token 不重排整个转录。全屏重绘在一次按键上花掉整屏刷新，读者看到的就是闪烁。

同一条契约决定了"临时提示"该放哪：确认信息与瞬时状态属于 composer 边框，不属于 transcript。写进 transcript 就等于写进不可改写的快照，一次操作确认会永久留在历史里。

同一份契约也约束**什么配得上整屏**。整屏是一种代价：读者正在读的对话被移走，退出时还要重新找回位置。因此整屏只给"放不下"的东西——需要翻页与搜索的长文档、有层级可展开的树、带预览的浏览列表。一个装得进 composer 卡片的选择不该占满屏幕，那只是把一次按键换成一次上下文切换。

这条判断属于渲染器，不属于调用点。十七个列表各自声明整屏，卡片窗口却早已知道自己能装多少行，重复的阈值一度散在两处命令里。列表只说"我是一个列表"，装不装得下由一处决定。

反过来，一个界面什么时候**必须**拥有自己的渲染器？判据同样是可检验的，不是行数，也不是审美：把必需的交互写成按键序列与状态/帧断言，如果它**在不改动通用卡片的公共类型、控制器或按键语义的前提下**无法通过，它就需要自己的控制器与视图，并复用纯粹的渲染原语（共享行、导航、边框）。能通过就用卡片。

三类交互在今天的接口下过不了这一关，所以它们不是"还没统一"，而是**不该统一**：设置的行内连续改值（`←→` 连续应用、`Ctrl+R` 恢复继承、字段表单的生命周期），trajectory 的账本状态机（分组折叠、独立详情视口、跟随与脱离跟随、多字段搜索按命中定位），Agent Hub 的双视口（宽屏两栏、窄屏切换焦点）。它们各自已经复用了共享的导航与行渲染——统一在**原语**层已经发生，不必再统一在**布局**层。

因此通用卡片的分界线是明确的：**选项、筛选、预览、选择结果、共享行与导航**。持续编辑、事件账本、双视口属于拥有它们的控制器。守住这条线的办法是拒绝三类新增：只为某一个调用方存在的开关；只能与另一字段搭配才合法、无法独立声明的组合；以及改变按键语义的请求。前两类会把接口重新养成 `TuiPrompt` 那四十多个可选字段——它已经被四个窄意图收敛过一次，不该再长回去。

## 附录

细节会过时，规则不会。以下两次故障是本文两条规则的来源，留作判据而非结论。

**`@` 菜单闪烁**（`51b9717`）。菜单由防抖搜索填充，而代码恰在该空档清空它，于是每击键闪一次。真正的失败有两个：三条路径改同一份状态且对"空结果"语义各异；以及缺少代次，使过期结果能覆盖新结果。

**`/files` 删除**（`83d7c88`）。全屏目录浏览在结构上可以是一个合法插件，但它服务的需求已被 `@` 补全、工具路径动作和 Changed files 覆盖。删除它确立的是范围原则，不是结构原则。

## 怎么用这份文档

改动前先定位它属于哪一层：

| 问题 | 归属 |
| --- | --- |
| 会话内容、工具语义、权限裁决错了 | Harness，不在 omdsh 修 |
| 某个事件画错了、折叠错了、宽度算错了 | 渲染层 |
| 一个键该做什么、哪一层被交还 | action catalog 与输入层 |
| 这个能力到底该不该有 | 本文"核心最小化"，默认不做 |

新增能力时，文档里必须能指出它挂在哪个既有扩展点上。指不出来，就是这条规则要拦住的东西。

## 与参考项目的关系

`refs/` 下的 pi、oh-my-pi 和 deepseek-harness 是研究材料，不是模板。此外横向观察过 codex、grok-build、minimax-code 等外部项目，那只是参照，不是本项目承认的参考基线——`AGENTS.md` 只承认 `refs/` 下的三个。

借用它们的**判断**，不借用它们的**形状**：`!` 命令该进原地卡片而不是全屏阅读器，这是判断；卡片长什么样由 omdsh 的转录、主题和 composer 决定。一个布局在几个参考项目里一致，只是证据，不是设计——它们面对的是各自的终端约束，omdsh 的约束由本仓库的历史契约和 DeepSeek 身份决定。同理，删除一个功能要给出"读者需求已被别处覆盖"的理由，而不是"别人也没做"。

允许链接到 `refs/` 作为证据。禁止把它们变成依赖、构建输入或运行时路径。
