# 设计哲学

omdsh 是 DeepSeek Harness 的终端。这份文档规定 omdsh 该做什么、不该做什么，以及做判断时依据什么。它排在其它设计文档之前：下面每一份文档都是它在一个具体领域的展开，冲突时以本文为准。

## 底座与消费者

DeepSeek Harness 拥有 agent、session、tool、policy、permission 和事件日志。omdsh 拥有终端呈现与输入。这条边界不是分工偏好，是 dsh 架构给出的定位：官方架构文档把"UI 或编辑器集成"归为 `drive ctx.agents, render from session/event`——驱动 agent，从事件日志渲染。

因此：

- **TUI 不产生模型会知道的任何东西。** 一条消息、一次工具调用、一个 turn 的边界，都源自 `SessionEvent`。TUI 可以补充只有终端才知道的事实（粘贴的字面意图、视口位置、终端能力），但不能发明会话内容。
- **TUI 不重新实现 Harness 的能力。** 权限判定、沙箱、审批规则、任务调度、反馈记录由已发布的包拥有。TUI 是这些服务的一个人机入口，不是它们的替代实现。
- **投影可以丢失，事实不能伪造。** 折叠、截断、预览都是呈现决定，读者随时可以展开回完整内容；反过来，把"没有收到结果"显示成"成功"是禁止的。

这条边界的实际含义：当一个问题看起来需要 TUI 自己维护状态才能解决时，先问它是投影问题还是事实问题。投影问题在渲染层解决，事实问题必须回到 Harness。

## 核心最小化

pi 的贡献是一句更强的话：核心必须小到能被扩展影响。dsh 的对应主张是"没有特权核心，一切挂载在旁"。两者指向同一个方向，omdsh 因此采用：

**核心只有三件事：**

1. **终端所有权。** 谁在什么时刻拥有 tty、哪些模式被开启和归还。这是不可委托的。
2. **不可省的最小交互。** 输入、提交、中断、退出，以及读一个必须由人回答的问题。
3. **事件投影。** 把 `SessionEvent` 变成有序的、可滚动的终端行。

**核心之外一律是插件、服务或消费者：**

命令、设置界面、工具呈现细节、外部集成、审核规则入口、副智能体巡览、模型推荐。它们通过 `ctx.commands`、`ctx.tui` 契约或事件挂载，卸载时随 Cordis effect 回退。

判断一个新能力该放哪，按这个顺序问：

- 它是否是 Harness 已经拥有的能力？→ 做成那个 service 的人机入口。
- 它是否只影响呈现？→ 放进渲染层，不要新增状态。
- 它是否需要自己的生命周期、可能在别的宿主里也成立？→ 独立 plugin。
- 以上都不是，它只是"TUI 里顺手加一下"？→ 默认不做。

最后一条是硬规则。`/files` 浏览器就是反例：它技术上可行，两个参考项目都没有，用户可以用 `@` 补全、工具路径和 Changed files 覆盖同一需求。它被删除了，因为它服务的是实现者能想到的场景，不是读者的真实需求。

## 单一投影原则

一个状态只能有一个写入方。

这是从一次真实故障得来的规则。`@` 补全菜单在每次按键时闪烁，根因是三条代码路径同时改同一份菜单状态：同步目录列表、防抖后的工作区搜索、以及"其余情况直接清空"。三条路径对"空结果"的语义各不相同——一条清空、一条等待、一条从不清空。故障定位花了五轮，因为读者看到的症状和任何单条路径的意图都不一致。

规则的形式化：**每份可变展示状态有一个所有者，其他代码只能通过它的方法请求变更，不能直接赋值。** 当一处状态需要被多条路径影响时，说明它被切分得不够——要么合并为一个有明确转换函数的状态机，要么拆成两个各自独立的状态。

这条规则同样约束"临时提示"：确认信息、瞬时状态属于 composer 边框，不属于 transcript。写进 transcript 就等于写进原生 scrollback，而那里是不可改写的快照。

## 呈现让位于内容

终端空间和读者注意力都是稀缺的。每一行 chrome、每一个提示、每一个模式，都要证明它换来的信息大于它占用的位置。

具体推论：

- **不重复。** 模型与推理强度已经在状态栏，header 不再显示。权限级别已经在 composer 边框右角，不在别处重复。
- **常驻提醒只留给不可能猜到的能力。** `Esc` 取消、`Enter` 发送，用一次就学会，不该占用 header 的唯一一行。`!` 跑 Shell、`@` 引用文件，猜不到，值得常驻。
- **状态用底色表达，不用标签堆叠。** 工具卡片的进行中/成功/失败是同明度三种色相，读者一眼分辨，不需要读一行字。
- **模式必须可见。** 任何改变提交含义的状态（Shell 模式、审查模式、被检视的子会话）都要在读者动手之前可见，而不是提交后才知道。
- **不把交互折叠成记忆题。** 需要选择时必须支持键盘选择，不能渲染一个编号菜单然后只留 composer 作为唯一入口。

## 原生历史是契约

终端自己的 scrollback 是历史，越过边界的行是**当时**的展示快照。折叠一个已完成的 run、一条工具调用落地、一次宽度变化，都不改写那些行。

这条契约有一个直接后果，也常被误认为缺陷：历史里的旧块与当前实时视图不同。那是预期行为。唯一允许的分界是显式的文档替换（`/clear`、会话切换、resume、fork），它在带标签的边界之后追加新文档，并保留此前的输出。

配合这条契约，呈现必须增量：已定型的行缓存，滚动和流式 token 不重排整个转录。全屏重绘在一次按键上花掉整屏刷新，读者看到的就是闪烁。

## 怎么用这份文档

改动前先定位它属于哪一层：

| 问题 | 归属 |
| --- | --- |
| 会话内容、工具语义、权限裁决错了 | Harness，不在 omdsh 修 |
| 某个事件画错了、折叠错了、宽度算错了 | 渲染层 |
| 一个键该做什么、哪一层被交还 | action catalog 与输入层 |
| 这个能力到底该不该有 | 本文"核心最小化"，默认不做 |

新增能力时，文档里必须能指出它挂在哪个既有扩展点上。指不出来，就是这条规则要拦住的东西。

## 与参考项目的关系

pi、oh-my-pi、codex、grok-build、minimax-code 是研究材料，不是模板。

借用它们的**判断**，不借用它们的**形状**：`!` 命令该进原地卡片而不是全屏阅读器，这是判断；卡片长什么样由 omdsh 的转录、主题和 composer 决定。三个参考项目都采用同一布局，那不构成理由——它们面对的是各自的终端约束，omdsh 的约束由本仓库的历史契约和 DeepSeek 身份决定。

允许链接到 `refs/` 作为证据。禁止把它们变成依赖、构建输入或运行时路径。
