# Terminal experience implementation

This work keeps the DeepSeek identity, native immutable scrollback, one terminal owner and the published Harness plugin boundaries. Existing Todo, subagent, approval and file readers remain the basis for the new interactions. Nothing is committed or published as part of this work.

## Verification and limits

Each stage updates English and Chinese product documentation and Unreleased. Focused behavior and fake-TTY tests precede the repository's full verification gates. Native terminal checks use the existing terminal appearance and isolated workspaces. Credentials are never printed and a keyless UI check does not establish provider authentication.

An unavailable public upstream API is recorded with the missing contract and evidence. Independent requirements continue; a workaround must preserve ownership and cannot import reference source or claim a capability it does not actually implement. Goal completion requires every row above to be implemented and verified, or an explicit user decision changing its scope.

## Brand palette and first-run readiness

The default terminal palette is derived from the public site tokens in `apps/site/src/styles/tokens.css`: DeepSeek blue `#4d6bfe` with the cyan gradient partner `#35c8de`, not the inherited amber/cyan scheme. `accent`, `border`, `borderAccent`, headings, links, list bullets, and the logo gradient follow that ramp; success, warning, error, code syntax, and card surfaces keep their semantic palettes. The light palette uses the site's light brand (`#3b57e0`). Contrast is enforced by `theme-contrast.spec.ts`, including fixed card backgrounds and representative host backgrounds.

The interactive host owns stdout and redirects plugin `console` calls to `$OMDSH_HOME/omdsh/logs/omdsh.log`; a plugin diagnostic must never write a raw line into the composer or corrupt the rendered frame. `omdsh exec` keeps its separate stdout/stderr protocol.

First-run readiness is optimistic and non-blocking. `modelRouteReady()` treats the upstream `DEEPSEEK_API_KEY`, a stored DeepSeek account grant, a configured `llm-pi-ai` provider profile, or a custom `apiKeyEnv` as connected; when both the settings and credentials seams are unavailable it also reports connected rather than guessing. Only a definite "no signal" answer changes the live composer placeholder to point at `/login`. The header is startup-stable and deliberately carries no transient readiness line, because rows that enter native scrollback must not be rewritten, and its hint line is a fixed catalog rather than a per-process sample. Credential and authorization changes recompute the placeholder, so a completed `/login` clears the hint without a restart.

## File recovery design constraints

The published `workspaceChanges` service serves live summaries and comparisons only; its records disappear when a Session is disposed. It does not export checkpoint creation, persistent manifests or restoration. The published `FileSystem` API reads bytes but writes only text (`writeText`/`editText`), with no binary-write, unlink or mode-restoration methods. These are concrete gaps for deleted and binary file recovery, not reasons to treat the existing summary as a checkpoint.

Recovery uses an omdsh-owned durable byte store and a local host provider, composed independently from its Session Tree consumer. Snapshots retain exact file bytes, ordinary regular-file mode bits, raw POSIX symbolic-link targets, explicit absent entries, high-resolution file revisions, workspace directory identity and a checksummed manifest. Git-aware capture includes tracked and nonignored untracked files in the active directory; ignored existing paths, submodules and embedded repositories are recorded as exclusions or protected boundaries. Non-Git capture walks the directory without following links. Git metadata and reserved recovery artifacts are always excluded. Empty directories, ownership, ACLs and extended attributes are outside the file-content contract. Hard links, special files, special permission bits, Windows reparse points, ambiguous path encodings, more than 10,000 files or exclusions, a file above 128 MiB, a snapshot above 1 GiB, an unstable scan or a manifest above 8 MiB reject the entire snapshot; no partial manifest is published. Private content-addressed blobs and manifests stay outside the workspace and survive process restart. Interrupted unpublished captures may leave unreferenced blobs; automatic pruning is not implemented.

A plan compares the before and after snapshots with the current host state. A later modification, identical-content rewrite, recreated deleted file, replaced directory parent or replaced workspace produces a conflict. A file that was excluded at Turn start is never inferred to be a creation when it later becomes visible. Protected boundaries are checked both in the snapshots and against the current Git inventory. Existing files already equal to the original snapshot need no write. Shell and external changes share the captured time window and must not be presented as edits attributed exclusively to the Agent.

Restoration uses the exact live owner’s public `runMaintenance` barrier. Every operation gets a durable intent before its worker runs. The host executes that worker through the published subprocess and sandbox APIs, always confined to the captured directory; Full access does not remove that confinement, and Read only prevents restoration. Recovery does not change the active working directory, Access or Git index. The worker rechecks the retained post-Turn version, verifies blob checksums, claims a present entry into a reserved backup and publishes by exclusive creation. A new path created during the publication gap is preserved, and a writer holding the old file descriptor retains its data in the original inode or backup. Displaced entries remain as `.omdsh-recovery-<operation-id>.backup` files. Cancellation drains the owned process and records cancelled or unconfirmed operations. A crash leaves planned entries whose completion is unconfirmed; it never proves success or triggers an automatic retry. The UI must expose partial results and backup locations. Per-file publication does not promise an all-files transaction.

Focused tests cover durable binary/create/delete snapshots, mode bits, links, later edits, concurrent writers, corrupt content, changed ignore rules, directory identity and actual confined workers through the published application composition. They also cover embedded repositories, active-directory capture and restoration after directory navigation. The full repository suite passed 2,192 tests before the final embedded-repository and unsupported-metadata adjustments; the latest kernel suite (13 tests) and public-provider suite (5 tests) pass. Installation, typecheck, build, Markdown, boundary, happy-smoke and PTY-smoke evidence passes; reference worktrees and dependency symlinks remain clean. The provider is mounted in the default product composition. Automatic capture is Off by default and enabled through Settings → Tools; only a Turn that begins with capture enabled receives a checkpoint. Live changes use the Harness volatile Config and affect the next Turn. A capture already started finishes when the switch is turned Off. A public-composition test verifies live changes and Profile persistence, and Turn-boundary tests prevent a mid-Turn enable from reopening an older checkpoint. Session Tree’s Alt+R selects files, previews retained contents, defaults confirmation to Cancel and returns per-file results. Alt+H exposes saved reports when available; conflicts and already-restored files still expose earlier reports. Interrupted workers without acknowledgement remain unconfirmed even when the file operation really completed. A non-waking source notice tells the model to reread recovered files on its next step. Portable session archives deliberately exclude these private snapshots and receipts.

The published API limitations are handled explicitly: file byte restoration uses the public confined subprocess seam, and an upstream partial-tree disposal gap produces a bounded failure rather than a successful cleanup claim. These are documented operating contracts, not pending implementations.
